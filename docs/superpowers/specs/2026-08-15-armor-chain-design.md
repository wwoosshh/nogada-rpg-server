# 방어구 사슬 설계 (아크 E)

> **For agentic workers:** 전투 §4(사용자 결정 2: 드랍 → 무기·**방어구** 사슬)의
> 남은 절반. 검이 증명한 패턴(드랍 재료 → 제작 → 강화 잉여 그물)을 방어구가
> 한 번 더 탄다 — 새 기계는 경감 식 하나뿐이다.

## 0. 왜 이 아크인가 (깨끗한 세션 추천 2)

- **방치 사망 실측 ~17s vs 설계 ~35s.** sweepDamage 를 깎는 미세조정은 몬스터가
  늘 때마다 반복될 빚이고, 방어구는 플레이어가 노가다로 갚는 구조적 답이다 —
  **설계의 35s 는 방어구를 낀 사람의 숫자가 된다**(§2 산술).
- **송곳니의 소비처가 외줄기다.** 가죽이 방어구(제작+강화 잉여)로 흐르면 전투
  드랍의 갈래가 둘이 되고, "검에 더 쓸까 방어구에 더 쓸까"라는 실제 선택이
  선다 — 원작의 "서로를 먹이는 시스템".
- **씨앗 ⑧(판로)을 여기서 닫는다** — 사냥 재료를 사 주는 상점이 이 아크의
  자연스러운 동반자다(§4).
- sweepDamage 재조정(⑮ 후보)은 **하지 않는다** — 방어구가 같은 문제를 노가다로
  풀므로, 지금 숫자를 깎으면 방어구의 값어치를 미리 깎는 이중 작업이 된다.

## 1. 방어구 = 도구 기계의 재사용 (C3 의 그 춤)

- `EquipSlot = SkillId | 'combat' | 'armor'` — 한 칸 추가. `EQUIP_SLOTS` 7칸.
  세이브 무해: `equipped` zod 는 열린 record(C3 에서 재현·증명된 그 성질).
- 방어구 아이템 = `kind: 'tool', toolSkill: 'armor', toolTier, defense: number`.
  파서: `toolSkill=armor` 는 `defense ≥ 1` 을 요구하고, armor 아닌 도구의
  defense 는 거절(combat/damage 의 그 대칭). "기술별 1티어 도구 하나" 검사는
  노드 계열 집합에서 나오므로 armor 는 구조적으로 밖이다(구현 평가 확인).
- **구현 평가가 짚은 파급 전수(스펙이 처음 빠뜨린 곳)**:
  ⑴ `parse.ts` `toEquipSlot` 이 'combat' 만 하드코딩 예외라 **armor 행을
  거절한다** — EQUIP_SLOTS 를 읽게 고친다. ⑵ `BagPanel` 슬롯 이름표
  `SKILL_LABELS[slot]` 이 컴파일 브레이크 — `slotLabelOf(EquipSlot)` 헬퍼
  하나로 전투/방어 라벨까지 소유시킨다. ⑶ `codexModel`·`shopModel` 의
  `Record<SkillId,…>` 인덱싱 두 곳도 같은 브레이크 — 가드 또는 좁히기.
- 강화·착용·예비·가방 전부 기존 기계 그대로 — 강화는 UL4(예비 동일 아이템 +
  enhance_costs t1 + 골드)라 **가죽 잉여 수요가 자동으로 선다**(검의 그 그물).

## 2. 경감 식 — shared 하나, 하한 1

```ts
/** 강화 +n 방어구의 경감 — 기본 defense + n (선형 +1, swingDamageOf 의 쌍둥이). */
export function armorDefenseOf(def: ItemDef, enhanceLevel: number): number {
  return (def.defense ?? 0) + enhanceLevel
}
```

- fightService ④(피격 루프): 걸린 배치마다
  `max(1, p.sweepDamage − armorDefenseOf(착용 방어구))` 를 합산. **하한 1** —
  경감이 피해를 0 으로 만들면 "회피 안 하면 맞는다"(§3·검사 3)가 장비로
  무력화된다. 위험은 언제나 아프다, 덜 아플 뿐이다.
- 소비자 셋이 한 식: 서버 판정(fightService) · 자동 착용 비교(isBetterTool
  armor 분기 — `armorDefenseOf(next,0) > armorDefenseOf(current, 강화)`) ·
  가방 표시(toolSpeedLabel armor 분기 `피해 −N`).
- **산술(설계 목표의 복원)**: 늑대 sweepDamage 20, 가죽옷 defense 5.
  뜨거운 칸 방치(주기당 피격 3): 맨몸 60/주기 → 사망 ~17s. 가죽옷 +0:
  45/주기 → ~22s. **+5: 30/주기 → ~33s ≈ 설계 35s.** 강화 사다리가 설계
  숫자를 되사 온다 — 그리고 검(+4·+5 죽은 단)과 달리 **방어구는 전 단이
  1씩 산다**(20−5−n 이 매 단 줄어든다): 죽은 단 없는 사다리.

## 3. 데이터 — 가죽·가죽옷·드랍

- `items.csv`: `wolf_pelt`(늑대 가죽, 매도가 20, 아이콘 눈으로 — 컨트롤러가
  몽타주에서 고른다) · `wolf_hide_armor`(늑대 가죽옷, toolSkill=armor, tier 1,
  defense 5, 아이콘 눈으로).
- `monster_drops.csv`: `wolf,wolf_pelt,0.35` 추가(합 0.85 ≤ 1 ✓ — 파서 검사 실재).
- `recipes.csv`: 가죽옷 = wolf_pelt×8 + copper_ingot×1 (category 도구,
  requiredSkill 0 — 검과 같은 부트스트랩 자세).
- **분-자**(평가 재계산 반영): 첫 가죽옷까지 **증분**(검 부트스트랩 종료
  숙련 ≈240 에서 이어, 미강화 검 = 2스윙/처치) 전투 활동 **2~6분** —
  기대 처치 8/0.35 ≈ 23회 × 실측 순환. combatBootstrap 은 맨손 모형
  하드코딩이라 재사용 불가 — **새 테스트**(armorBootstrap)를 같은 문법으로
  쓰고 시작 숙련·스윙/처치를 CSV·shared 에서 유도한다. 평가가 잰 부산물
  하나를 기록한다: **방어구 우선(맨손 3.9분)이 검 우선 누적(5.8분)보다
  빠르다** — 검이냐 방어구냐가 강제 순서가 아니라 실제 선택이다(트레이드
  오프: 방어구 우선은 이후 전투가 맨손으로 느리다).

## 4. 사냥 판로 (씨앗 ⑧ 종결) — 여관이 사 준다

- **새 화자 「사냥꾼」의 상점** — 여관 안주인 재사용은 **금지**다(평가 최우선
  성립): `openPendingShop` 은 상점 우선이라 한 화자가 상점·여관을 겸하면
  해금을 넘긴 순간부터 **여관이 영구 봉쇄**된다(gameStore 주석이 "지금
  데이터에는 없다"고 적어 둔 그 전제를 이 스펙이 처음 깨는 자리였다).
  사냥꾼은 눈의마을 동쪽 문 곁(사냥터 가는 길목, 좌표는 배치 검증이 무는
  걷는 칸)에 서는 새 speakers.csv 행이고, 스프라이트는 컨트롤러가 Male/
  몽타주에서 눈으로 고른다. shops.csv 한 행:
  `사냥상점,사냥꾼의 계산대,사냥꾼,combat,1000`.
  **해금 5,000 이 아니라 1,000 인 이유**(평가 산술): 전투 간격(하한 400ms)은
  채집(50ms)과 곡선 바닥이 달라 같은 5,000 이 실전투 ~171분 — 채집 상점
  체감(순수 손 14분대)과 완전히 다른 문이 된다. 1,000 ≈ 667스윙 ≈ 실전투
  ~34분 — 노드 아크의 30~60분 자에 드는 값이다. 원작 보존은 숫자가 아니라
  체감이다(원작은 권위가 아니다 — 같은 5,000 을 적으면 다른 문이 된다).
- `ShopDef.skill` 을 `SkillId | 'combat'` 로 확장(EquipSlot 의 그 춤).
  `isSellTarget` 은 그대로(`def.skill === shop.skill`) — 대신 `wolf_fang`·
  `wolf_pelt` 의 `skill` 칸에 `combat` 을 적는다(ItemDef.skill 도 같은 확장).
  **파급 목록(평가 반영 확정판)**: ⑴ 상점 해금 `shopAccess` — `player.skills
  [shop.skill]` 이 combat 에서 undefined 라 비교가 항상 false(문이 항상 열린
  것처럼) → combat 분기는 `combat.proficiency` 를 읽는다. ⑵ **stockUnlock 의
  `stockProgress` 도 같은 함정**(지금은 빈 진열이라 무증상 — 같은 분기 필요).
  ⑶ isSellTarget 은 동치 비교라 무수정. ⑷ 수집의 방: wolf_fang·wolf_pelt 는
  방 칸이 아니라 무영향(확인됨). ⑸ 아이템 skill 파서: SkillId ∨ 'combat'
  을 받는 **새 변환기**가 필요(toSkillId 도 toEquipSlot 도 이 모양이 아니다).
  ⑹ `shopModel.unlockLabelOf` 의 SKILL_LABELS 인덱싱 컴파일 브레이크.
- 진열(매수 품목)은 없다 — 상점은 사 주기만 해도 판로다. **구현 평가 실측:
  사기 탭은 빈 상태 처리가 아예 없어 빈 화면이 뜬다** — 팔기 탭의 "팔 것이
  없다" 와 대칭인 빈 상태 문구를 사기 탭에 추가한다(죽은 버튼 금지의 연장 —
  없는 것을 파는 척하지 않는 실제 패치).


## 5. 검증·닫음

- 관문 셋 + 태스크별 돌연변이(경감 하한 1 제거 → 기대 피격 0 재현, 경감 식
  제거 → 사망 산술 테스트 red, 판로 skill 확장 되돌림 → 매도 거절 red).
- 브라우저: **"뜨거운 칸 주기당 피격 3" 전제는 코드로 검증 불가 — 실측이
  §2 산술의 관문이다.** 가죽옷 착용 → 피격 -15(20−5) 플로트, +5 강화 상태 주입 → -10,
  가방 방어 칸 "피해 −N", 여관 상점에서 송곳니·가죽 매도(골드 증가), 해금
  전 상점 잠금 문구.
- 전체 브랜치 리뷰 → 푸시 → health.sha.
