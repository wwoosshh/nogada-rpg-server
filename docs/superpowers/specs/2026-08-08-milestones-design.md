# 이정표와 진척 목록 설계

**날짜:** 2026-08-08
**상태:** 서브에이전트 평가 반영 완료
**선행:** [숙련도 재설계](2026-08-03-proficiency-design.md), [모바일 조작](2026-08-08-mobile-controls-design.md)

---

## 1. 왜 이것이 다음인가

지금 게임에서 플레이어가 볼 수 있는 미래는 **없다.**

숙련도 숫자조차 화면 어디에도 안 나온다. 상단 바에는 시계뿐이다. 채집을 하면 무언가가 오르지만 그게 얼마인지, 어디로 가는지 알 수 없다.

그런데 **이미 열리는 것이 있다.** `recipes.csv` 는 조합 200 에서 구리 망치를, 조합 500 에서 철 도구 4종을 연다. 철 도구는 2등급 노드 4종을 열고, 그 노드들은 이미 맵에 놓여 있으며 새 재료 4종을 준다. 서버가 이것을 강제하고 있고 실제로 몇 분이면 닿는다.

**그런데 플레이어는 그런 것이 있다는 사실조차 알 수 없다.** 우연히 조합을 500 까지 하면 어느 날 목록에 새 레시피가 생겨 있을 뿐이다.

원작이 8,000시간을 버틴 이유는 반복이 무언가를 향하고 있었고 그 무언가가 **보였기** 때문이다. 지금 우리 게임에는 향하는 것이 있는데 보이지가 않는다.

---

## 2. 원작이 실제로 쓴 장치

원작 APK 의 이벤트 데이터를 직접 읽어 확인한 것만 적는다.

### 2.1 잠긴 것까지 보여주는 목록 — 확인됨

퀘스트 로그가 UI 가 아니라 **방**이다(Map177, NPC 약 30명). 각각이 위치·목표·드랍처·보상·진행도를 보여주고, `모든퀘보기` 스위치를 켜면 **아직 시작도 안 한 퀘스트까지** 미리 볼 수 있다.

업적방(Map342)도 같다. 기념비 앞에 서면 지금 등급과 **다음 등급까지 정확히 몇이 남았는지**를 한 줄로 알려준다.

> **주의 — 앞선 초안이 틀렸던 것:** 업적방이 "지나가다 보이는 곳" 이라고 적었는데 사실이 아니다. 20,000골드짜리 집을 사고 지하 2층까지 내려가야 나오는 **후반 콘텐츠**다. 반대로 퀘스트 목록은 메뉴 항목이었다. 즉 원작도 목록을 UI 로 뒀고, 방으로 만든 것은 나중의 업적 쪽이다.

### 2.2 잠긴 문이 요구치를 숫자로 말한다 — 확인됨

열리지 않는 문이 "안 됩니다" 로 끝나지 않는다. **플레이 1,000시간 + 걸음 2,000,000 + 레벨 99** 를 그대로 출력한다.

### 2.3 진짜 게이트는 산출물 자체를 바꾼다 — 확인됨, 그리고 이 설계가 놓칠 뻔한 것

원작에서 숙련도가 실제로 하는 일은 칭호를 주는 것이 아니다. **인라인 임계값이 채집 결과와 제작 가능 목록을 바꾼다.**

- 낚시 숙련도가 300/1,000/2,000/5,000 을 넘을 때마다 미끼 상인의 **상품 목록에 줄이 늘어난다**
- 요리 숙련도 100/1,000/10,000/100,000 이 레시피 등급을 연다
- 배달 숙련도가 보상 골드 계산식에 직접 들어간다 (`2500 + 숙련도÷5`)
- 상업 숙련도 5,000~50,000 이 판매가를 105%~130% 로 올린다

**칭호는 장식이고, 게이트가 콘텐츠다.** 목록이 칭호만 나열하면 원작이 한 일의 껍데기만 가져오는 것이다.

### 2.4 이정표가 서로를 합산한다 — 확인됨

기술마다 5단계 칭호가 있고, 그것이 합산된다.

- 얼음달인 + 허브달인 + 나무달인 + 광물달인 + 낚시달인 이 **전부** 켜지면 → `채집달인` (Map342 이벤트 7)
- 다섯 계층이 같은 방식으로 `채집신` 까지 올라간다
- `채집신` + `균형신` + `수집신` + `무덤신` + 조합·대장·레벨·영웅·**재산** 등 **15개 최상위**가 전부 켜져야 → `업적의신` 이 단 하나의 보상을 준다 (Map019 이벤트 77)

여기에 `균형` 축이 따로 있다. 채집 네 기술이 **각각** 같은 문턱을 넘어야 달성된다 — 하나만 파는 사람은 영원히 못 받는다.

배우는 것: 사다리가 자기 안에서 끝나면 안 된다. **사다리를 만들되 그 위에 얹히는 층을 함께 만든다.**

### 2.5 문턱이 촘촘하고, 축마다 박자가 다르다 — 확인됨

원작 얼음 사다리: **63,235 / 500,000 / 1,000,000 / 2,500,000 / 5,000,000**. 79배 폭에 다섯 단이 들어간다.
원작 균형 사다리: **10,000 / 100,000 / 300,000 / 600,000 / 1,000,000**. 완전히 다른 박자로 따로 돈다.

한 축이 비어 있는 동안 다른 축이 채운다. 이것이 "다음에 뭐가 있을까" 를 끊기지 않게 하는 방법이다.

## 3. 이 설계가 만드는 것

### 3.1 이정표 (Milestone)

플레이어 상태가 조건에 닿는 순간을 데이터로 선언한다.

```ts
interface MilestoneDef {
  id: string
  metric: MilestoneMetric
  threshold: number
  name: string
  /** 달성했을 때 화면에 뜨는 한 문장 */
  announce: string
  effect: MilestoneEffect
}

type MilestoneMetric =
  | { kind: 'skill'; skill: SkillId }
  | { kind: 'every'; of: string[] }   // 나열된 이정표를 전부 달성했는가
  // 이후 스펙이 더한다: 걸음 수, 플레이 시간, 소지 골드 …

type MilestoneEffect =
  | { kind: 'repeat' }                         // 그 기술의 자동 반복이 열린다
  | { kind: 'recipes'; ids: string[] }         // 이 레시피들을 만들 수 있게 된다
  | { kind: 'nodes'; ids: string[] }           // 이 노드들을 캘 수 있게 된다
  | { kind: 'title' }                          // 이름만. 효과 없음
```

`recipes` 와 `nodes` 는 **새 게이트를 만드는 것이 아니다.** 이미 `recipes.csv` 의 `requiredSkill` 과 도구 등급이 강제하고 있는 것을 **목록에 보이게 하는 것**이다. 이정표가 그 게이트를 *선언*하고, 검증이 데이터와 어긋나지 않는지 확인한다.

이렇게 하면 목록의 첫 화면부터 질적으로 다른 줄이 섞인다 — "칭호를 받는다" 와 "철 곡괭이를 만들 수 있게 된다" 는 플레이어에게 완전히 다른 무게다.

지금 하드코딩돼 있는 자동 반복 해금은 이 모델의 한 인스턴스가 된다.

### 3.2 목록은 B 버튼의 상세 메뉴 안에 있다

**B 버튼이 상세 메뉴가 된다.** 탭으로 나뉘고, 이정표 목록은 그중 한 탭이다.

| 탭 | 내용 |
|---|---|
| 숙련도 | 다섯 기술의 현재 숙련도, 행동 간격, 성공률 |
| 이정표 | 이 설계가 만드는 목록 |
| 설정 | 지금 상단 바 우측 톱니에 있는 것 |

나중에 이벤트·퀘스트 집계가 탭으로 더해진다.

**원작이 정확히 이 구조였다.** 특수 메뉴를 호출하는 커먼이벤트의 이름이 `[★B]특수메뉴호출` 이고, 숙련도 정보 화면(`[☆★]숙련도정보`)이 그 메뉴 안에 있다. 원작의 오른쪽 버튼 묶음에도 "특수 메뉴" 버튼이 따로 있었다.

이렇게 하면 두 가지가 같이 풀린다. 오른쪽 버튼 묶음에 다섯 번째 버튼을 더하지 않아도 된다 — 엄지 도달 범위를 넘길 뻔했다. 그리고 상단 바의 톱니를 메뉴 안으로 넣거나 메뉴를 여는 두 번째 입구로 만들 수 있어, 3.3 의 한 줄이 쓸 가로 공간이 생긴다.

**B 의 의미는 하나로 유지한다.** 무언가 열려 있으면 닫고, 아무것도 없으면 상세 메뉴를 연다 — 휴대폰 뒤로 가기와 같은 규칙이다.

목록 자체는 **달성한 것과 아직 못 한 것을 함께** 보여준다.

- 달성한 것: 이름과 무엇이 열렸는지
- 못 한 것: 이름, 무엇이 열리는지, **지금 값과 필요한 값**

**"???" 를 쓰지 않는다.** 2.2 와 같은 이유다.

정렬은 남은 비율이 작은 순이다. 다음에 닿을 것이 맨 위에 온다.

> 원작의 업적방이 후반 콘텐츠였다는 사실(2.1)이 패널 선택을 뒷받침한다. 목록을 방으로 만드는 것은 마을이 생긴 뒤에 검토한다.

### 3.3 다음 하나는 패널 밖에 항상 떠 있다 — 이 설계에서 가장 중요한 부분

패널은 열어야 보이고, **패널이 열려 있는 동안에는 이동과 행동이 막힌다**(모바일 조작 설계 7장). 즉 진척을 확인하려면 진척을 멈춰야 한다. 그것만으로는 "다음에 뭐가 있을까" 가 생기지 않는다.

**상단 바에 다음 이정표 한 줄을 상시 표시한다.**

```
[다음 · 광물 숙련  8,240 / 10,000]                    [⚙]
```

원작의 기념비도 정확히 이 한 줄이었다("다음업적 : 얼음숙련50만"). 가장 가까운 이정표 하나만 보여주고, 채집할 때마다 숫자가 움직인다. **채집하는 화면에서 목표가 보이는 것**이 이 시스템의 전부다.

이것은 숙련도를 화면에 처음 노출하는 일이기도 하다. 지금 상단 바에는 시계밖에 없다.

### 3.4 서버가 달성을 판정하고, 달성 여부는 저장하지 않는다

**달성은 저장하지 않는다.** 모든 지표가 단조 증가하므로 달성 여부는 `PlayerState` 의 **순수 함수**다. 저장하면 저장한 것과 계산한 것이 어긋날 수 있고, 이정표 id 가 바뀔 때 세이브가 깨진다.

저장하는 것은 **"이미 축하했는가" 하나뿐이다.** 이것은 틀려도 피해가 없다 — 최악의 경우 축하가 한 번 더 뜨거나 한 번 안 뜬다.

판정은 서버가 한다. 서버가 행동을 처리한 뒤 새로 달성된 것을 찾아 응답에 실어 보내고, 클라이언트는 받은 것을 표시할 뿐이다. 나중에 이정표가 실제 보상을 줄 때 그 **축하 원장이 그대로 지급 원장이 된다** — 두 번 주지 않기 위해 필요한 것이 정확히 그것이다.

## 4. 무엇을 만들지 않는가

- **골드·상점·경제.** `MilestoneEffect` 에 자리를 만들지 않는다. 경제 스펙이 그때 더한다.
- **퀘스트.** 이정표는 "숫자가 닿으면" 이고 퀘스트는 "무엇을 하면" 이다.
- **숙련도 외의 지표.** `metric` 을 열어 두되 지금은 기술 숙련도와 합산만 본다.
- **새 게이트.** 이정표는 이미 존재하는 게이트를 선언할 뿐 만들지 않는다.
- **목록을 방으로 만드는 것.** 마을이 생기면 검토한다.

### 자동 반복의 서버 강제는 이번 범위가 아니다

초안은 여기서 "조작된 클라이언트가 자동 반복을 훔칠 수 있으니 서버가 막자" 고 적었다. 두 가지 이유로 뺀다.

첫째, 제안한 방법(요청에 "반복이다" 를 실어 보내기)이 아무것도 막지 못한다. 그 표시를 안 붙이면 그만이다.

둘째, **훔칠 것이 없다.** 행동 간격은 숙련도만의 함수이고 서버가 그것을 강제한다. 자동 반복은 속도를 주지 않고 손가락을 대신할 뿐이다. 조작된 클라이언트가 얻는 것은 편함이지 이득이 아니다.

진짜로 닫아야 하는 것은 위치 검증(인접·바라봄)이고, 그것은 위치 동기화 스펙의 일이다.

## 5. 이정표 데이터

두 축을 둔다. 하나가 비는 동안 다른 하나가 채우게 하려는 것이다(2.5).

**축 A — 기술별 사다리.** 촘촘하게 둔다. 우리 곡선 기준 도달 시간을 함께 적는다.

| 지표 | 문턱 | 도달 | 무엇 |
|---|---|---|---|
| 각 채집 기술 | 1,000 | 약 5분 | 칭호 |
| 각 채집 기술 | 10,000 | 약 31분 | 자동 반복 |
| 각 채집 기술 | 50,000 | 약 1.8시간 | 칭호 |
| 각 채집 기술 | 200,000 | 약 5시간 | 칭호 |
| 각 채집 기술 | 1,000,000 | 약 16시간 | 칭호 (최고속 도달) |

**축 B — 조합과 합산.** 다른 박자로 돈다.

| 지표 | 문턱 | 무엇 |
|---|---|---|
| 조합 | 200 | 구리 망치를 만들 수 있다 *(이미 `recipes.csv` 가 강제 중)* |
| 조합 | 500 | 철 도구 4종을 만들 수 있다 *(같음)* → 2등급 노드 4종이 열린다 |
| 조합 | 10,000 | 자동 반복 |
| 조합 | 100,000 | 칭호 |
| **채집 4종이 각각** 1,000 | — | 칭호 (첫 합산) |
| **채집 4종이 각각** 10,000 | — | 칭호 (균형) |
| **채집 4종이 각각** 200,000 | — | 칭호 |

> **원작 수치와의 관계.** 합산 축의 10,000 은 원작 균형달인의 문턱과 우연히 같다. 우리 값은 "행동 간격이 200ms 가 되는 지점" 에서 독립적으로 나온 것이고 원작에서 가져온 것이 아니다. 원작의 수치·데이터를 쓰지 않는다는 프로젝트 제약(설계 1.2)을 지킨 상태다.

**칭호만 주는 이정표는 칭호만 준다고 목록에 적는다.** 효과가 없다는 사실이 데이터에 있고 화면에 보여야 한다.

## 6. 열린 질문

1. **다섯 기술을 고르게 하는 것이 실제로 즐거운가.** 합산 축은 전문화를 벌한다. 원작에는 그것이 있었지만, 원작에는 기술이 스물이 넘었고 우리는 다섯이다. 실제로 해 보고 판단한다.
2. **상단 한 줄이 하나로 충분한가.** 지표가 늘면 "다음 세 개" 가 필요해질 수 있다. 가로 화면의 가로 공간은 여유가 있지만 시선은 그렇지 않다.
3. **16시간 문턱이 정당한가.** 축 A 의 마지막 칸은 최고속 도달 지점이라 의미가 있지만, 5시간에서 16시간 사이가 여전히 비어 있다. 콘텐츠가 늘면 그 사이를 다른 축이 채워야 한다.
