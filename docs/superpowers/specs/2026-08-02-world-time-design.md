# 세계 시간 시스템 — 설계 문서

**작성일:** 2026-08-02
**상태:** 승인됨 (구현 계획 대기)
**관련 문서:** [노가다RPG 팬메이드 설계](2026-08-02-nogada-rpg-fanmade-design.md)

---

## 1. 개요

### 1.1 목적

게임 안에 자체적인 날짜와 시간을 흐르게 해서, 시간대에 따라 이벤트가 발생하거나 대사가 달라지는 등 **세계가 살아 있어 보이게** 한다.

### 1.2 이 문서의 범위

시간 엔진, 화면 표시, 낮밤 명암까지다. 시간에 반응하는 **콘텐츠**(계절별 채집물, NPC 일과, 밤 전용 몬스터)는 여기서 만들지 않는다. 이 문서는 그것들이 나중에 얹힐 **토대**를 놓는다.

같은 작업에 딸린 화면 정리도 포함한다 — 기존 UI 패널 제거, 가로 방향 고정.

### 1.3 원작에는 이 시스템이 없다

원작 APK(v2.1, RPG Maker XP/RGSS1)를 해석해 확인했다. **원작에 게임 내 달력이나 낮밤 개념은 없다.**

원작의 「시간」 변수는 전부 **현실 플레이 시간 카운터**이며, `현재플레이시간` 과 `다음~시간` 을 짝지어 쿨다운을 재는 용도로만 쓰인다 (채집 부스터, 상점 재입고, 이동 제한 등). 계절·요일·시간대 변수는 하나도 없다.

따라서 이 시스템은 **이식이 아니라 창작**이다. 맞춰야 할 원작 동작이 없으므로 수치와 구조를 자유롭게 정할 수 있고, 반대로 「원작은 어땠나」로 검증할 수도 없다 — 재미 판정은 직접 플레이로만 가능하다.

### 1.4 비목표

- 계절별 채집물 게이팅 (숙련도 재설계 이후)
- NPC 대사 데이터 구조 (맵에 NPC가 없다)
- 시간 조작 치트 방지 이상의 보안
- 플레이어별 시간 흐름(가속·정지) — 세계 시간은 모두에게 하나다

## 2. 확정 요구사항

| 항목 | 결정 |
|---|---|
| 시간 배율 | 현실 1시간 = 게임 하루 |
| 달력 단위 | 시간대 + 일 + 계절 + 년 |
| 계절 길이 | 28일 (4계절 = 1년 = 112일) |
| 시각의 권위 | **서버 시계** |
| 1차 구현 범위 | 시간 엔진 + 상단 표시 + 낮밤 명암 |
| 화면 방향 | **가로 고정** |
| 행동 피드백 | 캐릭터 머리 위 플로팅 텍스트 |

## 3. 시간 모델

### 3.1 수치

| | 값 | 현실 환산 |
|---|---|---|
| 게임 하루 | 24시간 | 현실 1시간 |
| 게임 1시간 | 60분 | 현실 2분 30초 |
| 게임 1분 | — | 현실 2.5초 |
| 한 계절 | 28일 | 현실 28시간 |
| 1년 | 4계절 = 112일 | 현실 약 4.7일 |

계절은 봄·여름·가을·겨울. 표기 예: `3년차 봄 12일 07:30`.

**28일을 고른 근거:** 1년이 현실 4.7일이라 모든 계절을 며칠 안에 겪는다. 계절마다 성격이 분명해질 만큼 길면서도, 특정 계절을 영영 못 보는 일은 없다.

**나중에 조정할 여지:** 「얼음 = 겨울에만」 같은 계절 게이팅을 걸면 겨울이 4.7일에 한 번, 28시간만 열린다. 잠금을 실제로 도입할 때 14일로 줄이는 것을 재검토한다. 상수 하나이므로 변경 비용은 낮다 — 다만 **바꾸면 진행 중인 세계의 날짜가 통째로 어긋나므로** 서비스 시작 전에 확정해야 한다.

### 3.2 시간대 구분

| 시간대 | 게임 시각 | 현실 지속 |
|---|---|---|
| 새벽 | 04:00–05:59 | 5분 |
| 아침 | 06:00–09:59 | 10분 |
| 낮 | 10:00–17:59 | 20분 |
| 저녁 | 18:00–20:59 | 7분 30초 |
| 밤 | 21:00–03:59 | 17분 30초 |

이 구간 이름은 **조건 판정용**이다 (「밤에만 나오는 채집물」). 화면 명암은 이 구간으로 끊지 않고 3.4의 연속 함수를 쓴다.

### 3.3 기준점

`GAME_EPOCH_MS` 상수 하나가 「1년차 봄 1일 00:00」에 해당하는 실제 시각(epoch ms)을 정한다.

**이 값은 한 번 정하면 바꾸지 않는다.** 바꾸면 모든 플레이어의 「며칠째」가 어긋나고, 날짜에 묶인 기록(거래 이력, 이벤트 로그)의 의미가 소급해서 변한다.

### 3.4 명암 곡선

밤이 가장 어둡고 정오가 가장 밝다. 구간 경계에서 화면이 갑자기 어두워지지 않도록 **분 단위 시각을 입력받는 연속 함수**로 어둠 정도(0~1)를 계산한다.

색조도 함께 바꾼다 — 밤은 짙은 남색, 새벽·저녁은 옅은 주황. 낮에는 오버레이가 사실상 투명하다.

## 4. 아키텍처

### 4.1 시각의 권위는 서버 시계다

```
서버 벽시계(now) ─┐
                  ├─→ gameTimeAt(now) → GameTime
GAME_EPOCH_MS    ─┘   (packages/shared, 순수 함수)
```

`gameTimeAt` 은 **순수 함수**이며 `packages/shared` 에 한 번만 둔다. 서버와 클라이언트가 같은 함수를 import 한다 — 이 프로젝트가 채집·제작 공식에 이미 쓰고 있는 규칙과 같다.

권위 문제는 「공식이 무엇인가」가 아니라 **「어떤 실제 시각을 넣느냐」**이며, 그 답이 서버 시계다.

**왜 서버인가:** 이 게임은 한 화면에 여러 플레이어가 보이고 거래소를 공유할 예정이다. 각자 기기 시계로 계산하면 같은 자리에 선 두 사람이 다른 세계 시각을 보게 되고, 거래소 마감이나 시간 제한 이벤트가 붙는 순간 분쟁이 된다. 기기 시계는 수동 설정·NTP 오차·시간대 설정으로 얼마든지 어긋난다.

### 4.2 클라이언트 시각 동기화

클라이언트는 자기 `Date.now()` 를 세계 시각으로 쓰지 않는다. 서버와의 **오프셋을 재서** 따라간다.

```
t0 = 클라 현재      →  GET /api/time  →  { serverNowMs }  →  t1 = 클라 현재
rtt = t1 - t0
서버 시각 추정 = serverNowMs + rtt / 2        (편도가 왕복의 절반이라고 가정)
앵커 = { serverMs: 서버 시각 추정, perfMs: performance.now() }
```

이후 세계 시각은 다음으로 계산한다.

```
worldNow() = 앵커.serverMs + (performance.now() - 앵커.perfMs)
```

**`Date.now()` 가 아니라 `performance.now()` 로 경과를 재는 이유:** 세션 도중 사용자가 기기 시계를 바꿔도 세계 시각이 튀지 않는다. `Date.now()` 기반이면 시계를 한 시간 앞당기는 순간 게임 안에서 하루가 지나간다.

**재동기 시점**

| 시점 | 이유 |
|---|---|
| 앱 시작 | 최초 앵커 |
| 백그라운드 → 복귀 | 모바일에서 가장 자주 어긋나는 지점. 절전 중에는 JS 실행이 멈춘다 |
| 주기적 (5분) | 느린 드리프트 보정 |
| API 응답 편승 | 모든 응답에 `serverNowMs` 를 실어 채집·제작 때마다 공짜로 갱신 |

편승 갱신은 왕복 시간을 별도로 재지 않으므로 **앵커를 교체하지 않고**, 추정 오차가 임계값(예: 2초)을 넘을 때만 재동기를 유발한다. 매 응답마다 앵커를 갈아끼우면 왕복 시간 흔들림이 그대로 시계 떨림으로 나타난다.

### 4.3 판정은 서버 시계로만 한다

시간에 묶인 판정(밤 전용 채집물, 계절 게이팅, 이벤트 발생)은 **서버가 자기 시계로 수행**한다. 클라이언트가 보낸 시각을 신뢰하지 않으며, 요청 본문에 시각을 담지 않는다.

클라이언트의 세계 시각은 **표시 전용**이다. 이는 난수에 이미 적용하고 있는 규칙과 같다 — 클라는 예상치를 그리고 판정은 서버가 한다.

### 4.4 오프라인 모드

설계 문서 3.4는 「서버를 내려도 게임이 죽지 않는다」를 약속한다. 오프라인에서는 공유할 세계가 없으므로 **오프셋 0으로 로컬 시계를 그대로 쓴다.** 온라인 접속 시 서버 시각으로 스냅된다.

## 6. 화면

### 6.1 상단 상태 바

가로 화면 상단에 얇게 배치한다. 좌측에 `봄 12일 · 07:30`, 우측 끝은 **설정 버튼 자리로 비워둔다** (설정 메뉴는 별도 작업).

게임 1분(현실 2.5초)마다 갱신한다. 초 단위로 갱신하면 재렌더 비용만 늘고 읽는 사람에게 의미가 없다.

### 6.2 낮밤 명암

화면 전체를 덮는 사각형 하나를 카메라에 고정(`setScrollFactor(0)`)하고, 3.4의 함수로 계산한 색과 투명도를 적용한다.

### 6.3 행동 피드백 — 플로팅 텍스트

기존 `Feed` 패널을 대신해 **캐릭터 머리 위에서 떠오르며 사라지는 글자**로 결과를 알린다. 화면을 가리지 않고, 가로 화면에서 시선이 캐릭터에 머무는 것과 맞다.

| 상황 | 표시 |
|---|---|
| 채집 성공 | `구리 원석 +2` |
| 채집 실패 | `실패` |
| 쿨다운 중 | **아무것도 표시하지 않는다** |
| 제작 성공 | `구리 주괴 +1` (자동 착용 시 `자동 착용` 추가) |
| 제작 실패 | `제작 실패` |

**쿨다운을 조용히 무시하는 이유:** 아직 회복되지 않은 노드를 누르는 것은 실수가 아니라 정상적인 조작이다. 매번 경고를 띄우면 연타할수록 화면이 경고로 덮인다.

**경험치를 표시하지 않는 이유:** 숙련도를 1행동 = +1 방식으로 바꿀 예정이라(별도 작업) 지금 숫자를 띄워도 곧 무의미해진다. 서버는 여전히 경험치를 계산하지만 메시지에서만 뺀다.

### 6.4 Phaser 가 결과를 아는 방법

게임 상태의 단일 소유자는 여전히 `gameStore` 다. 씬이 자체 상태를 갖지 않도록, 스토어가 **마지막 행동 결과**를 담고 씬은 zustand `subscribe` 로 그 변화만 구독한다. 씬은 「떠오르는 글자를 그리는 일」만 한다.

폴링하지 않는 이유는 결과가 프레임과 무관하게 도착하기 때문이다 — `update()` 에서 매 프레임 확인하면 같은 결과를 두 번 그리지 않도록 소비 여부를 씬이 따로 기억해야 하고, 그게 곧 씬이 상태를 갖는 것이다.

### 6.5 렌더 깊이

```
ground 0 · decor 1 · walls 2 · node 5 · player 10 · overhead 20
· dayNight 30 · floatingText 40
```

**플로팅 텍스트를 명암보다 위에 두는 이유:** 밤에 글자까지 어두워지면 읽히지 않는다. 피드백은 연출보다 우선한다.

## 7. 제거하는 것

`SkillBar` · `Inventory` · `CraftPanel` · `Feed` 컴포넌트와 관련 CSS를 삭제하고 `App` 에서 뺀다. `ItemIcon` 은 나중 패널에서 재사용하므로 남긴다.

인벤토리와 제작은 **컨트롤러 버튼으로 열고 닫는 패널**로 다시 만든다 (별도 작업). 지금 구조를 남겨두면 새 설계와 섞여서 오히려 방해가 된다.

스토어의 `gather` · `craft` 액션과 셀렉터는 그대로 둔다. 지워지는 것은 화면 구성뿐이다.

---

## 8. 화면 방향

`AndroidManifest.xml` 에 가로 고정을 넣는다.

설계 문서 4.2의 32×32 선정 근거가 **세로 화면 기준**(`360×640 → 11×20 타일`)으로 적혀 있으므로 가로 기준(`640×360 → 20×11 타일`)으로 고친다. 타일 크기 결정 자체는 유지된다 — 가로에서도 20×11이면 시야가 충분하다.

## 9. 테스트

| 대상 | 방식 |
|---|---|
| `gameTimeAt` | 유닛 테스트. 자정, 계절 마지막 날 23:59 → 다음 계절 1일 00:00, 연말 → 다음 해, epoch 이전 시각 |
| `timeOfDay` | 구간 경계값 (03:59/04:00, 20:59/21:00) |
| `darkness` | 단조성(정오 최소, 자정 최대)과 경계 연속성 |
| 오프셋 계산 | 순수 함수로 분리해 테스트. 왕복 보정, 임계값 판정 |
| `GET /api/time` | 라우트 테스트 |
| 화면 (상태 바·명암·플로팅 텍스트) | **자동 테스트하지 않는다.** 기존 방침대로 수동 검증 |

## 10. 이 문서 밖 — 결정 시점

| 항목 | 시점 | 기준 |
|---|---|---|
| 계절 길이 재조정 (28 → 14) | 계절 게이팅 도입 시 | 특정 계절 잠금이 실제로 답답한지 |
| `GAME_EPOCH_MS` 확정값 | 서비스 시작 전 | 시작 후에는 바꿀 수 없다 |
| 시간대별 대사·이벤트 데이터 구조 | NPC 도입 시 | 맵에 NPC 가 생긴 뒤 |
| 시간 가속·정지 (디버그용) | 필요해질 때 | 개발 편의. 운영 서버에는 넣지 않는다 |
