# 노가다RPG 팬메이드 — 설계 문서

**작성일:** 2026-08-02
**상태:** 승인됨 (구현 계획 대기)

---

## 1. 개요

### 1.1 목적

「노가다 RPG」(인디사이드, RPG Maker XP 기반, 서비스 종료)와 **같은 계열의 생활기술 중심 온라인 RPG**를 새로 만든다.

### 1.2 성격

원작의 **복원이 아니라 창작**이다. 원작은 장르적 참조점일 뿐이며, 리소스·데이터·시스템 수치는 전부 자체 제작한다. 원작의 그래픽·음악·데이터를 가져다 쓰지 않으므로 저작권 문제가 발생하지 않는다.

### 1.3 비목표 (Non-goals)

명시적으로 이번 범위에 넣지 않는 것들:

- 원작 데이터·리소스의 복원 또는 이식
- 실시간 파티 전투·공동 보스 (v2에서 재검토)
- PvP
- 3D 렌더링
- iOS 출시 (안드로이드 우선, iOS는 v2)
- 결제·과금 시스템

## 3. 기술 스택 및 아키텍처

### 3.1 스택 선정 근거

후보는 (A) TypeScript 풀스택, (B) Unity + TS 서버, (C) Godot 4 + TS 서버였다. **A안을 선택**한 결정적 이유는 **게임 규칙을 몇 번 구현하는가**이다.

서버 권위 구조에서 클라이언트도 "예상 데미지", "제작 성공률", "다음 레벨까지 필요 숙련도"를 표시해야 한다. 언어가 갈리면 같은 공식을 두 언어로 중복 구현하게 되고, 밸런스를 수정할 때마다 두 곳을 고쳐야 하며, 어긋나면 "표시값과 실제값이 다른" 버그가 발생한다. 밸런스 수정이 일상인 노가다 장르에서 이 비용은 프로젝트 내내 복리로 누적된다.

부차적 이유:
- UI를 HTML/CSS로 작성 → 이 장르의 최대 비용 항목(수십 개의 UI 화면)을 가장 싸게 해결
- 개발자의 기존 역량(TS/JS)을 100% 활용, 1인 개발에서 컨텍스트 스위칭 비용 제거

RPG Maker MZ는 온라인 + 모바일 요구사항으로 인해 후보에서 제외되었다. (전역 싱글톤 상태 구조라 서버 권위 도입 시 엔진 재작성 수준, 기본 배포 대상이 Windows/macOS/웹이라 모바일은 별도 래핑 필요)

### 3.2 모노레포 구조

```
nogadaRPG_fanmade/            pnpm workspace
├─ apps/client                Phaser(렌더·타일맵) + React(UI) + Vite
│                             → Capacitor로 안드로이드 래핑
├─ apps/server                Node + TS / Fastify(REST) + WebSocket
├─ packages/shared            전투 공식, 성공률 계산, 숙련도 곡선, zod 스키마
├─ packages/data              CSV → 검증 → 타입 있는 JSON
└─ docs/                      설계 문서, 밸런스 노트
```

### 3.3 계층 구조

```
apps/client  ── Capacitor WebView / 브라우저
  Phaser ────── 맵, 캐릭터, 채집 노드, 이펙트
  React ─────── 인벤토리, 제작, 강화, 도감, 거래소, 채팅
  GameClient ── 서버 통신 단일 진입점 (REST + WebSocket)
        │
        │  REST(행동 요청) + WS(위치·채팅)
        │
apps/server  ── Node + TypeScript
  게임플레이 ── 채집 · 제작 · 강화 · 전투 판정      [서버 권위]
  경제 ──────── 거래소 · 우편 · 인벤토리 트랜잭션   [서버 권위]
  presence ──── 위치 브로드캐스트 · 채팅            [신뢰 불필요]
        │
  PostgreSQL ── 플레이어, 인벤토리, 거래 원장
```

### 3.4 핵심 설계 결정

**① 판정은 전부 서버. 클라는 같은 함수로 "예상치"만 그린다.**

`packages/shared`에 `calcGatherChance()`, `calcCraftSuccess()`, `calcDamage()`, `xpToNext()`를 한 번 작성하고 서버·클라가 동일 코드를 import 한다. 서버는 이것으로 실제 판정하고, 클라는 이것으로 툴팁의 성공률을 그린다. 공식이 하나뿐이므로 표시값과 실제값이 어긋날 수 없고, 밸런스 수정 시 한 곳만 고치면 된다.

**② 난수 시드는 서버가 독점한다.**

채집 성공, 드롭, 강화 성패는 전부 서버가 굴리고 결과만 내려준다. 클라이언트의 연출은 결과가 확정된 뒤 재생되는 애니메이션에 불과하다. 클라에서 난수를 굴리면 결과 조작이 가능하다.

**③ 이동과 채팅은 검증하지 않는다.**

다른 플레이어 아바타는 게임 로직에 영향이 0이다. 위치를 조작해도 남들 화면에서 이상한 위치에 서 있는 것이 전부다. 여기에 검증을 넣으면 서버 비용만 폭증한다. **신뢰가 필요한 경계와 아닌 경계를 명확히 분리하는 것이 이 아키텍처의 핵심이다.**

**④ 서버 주소는 환경변수 하나. 그래서 게임이 죽지 않는다.**

서버 로직이 TypeScript이므로 클라이언트 번들에 포함시킬 수 있다. 동일 코드가 세 모드로 동작한다:

| 모드 | 동작 |
|---|---|
| 개발 | `localhost` 서버에 접속 |
| 운영 | 원격 서버에 접속 |
| **오프라인** | 서버 코드를 인프로세스 실행, 인터넷 없이 싱글 플레이 |

원작이 서비스 종료로 사라진 것과 달리, 이 구조에서는 **서버를 내려도 게임이 죽지 않는다.** 거래소와 채팅만 사라진다. 이는 나중에 추가하는 기능이 아니라 지금 경계를 어떻게 긋느냐로 결정되는 속성이다.

### 3.5 이 구조의 대가

- **Phaser + React 상태 동기화**: 게임 상태의 단일 소유자(클라 측 스토어 하나)를 정하고 Phaser와 React 둘 다 거기만 바라보게 한다. 위반 시 "인벤토리 UI엔 반영됐는데 맵엔 안 됐다" 류 버그가 발생한다.
- **Capacitor WebView 성능**: 네이티브보다 느리다. 맵당 동시 스프라이트 상한과 텍스처 아틀라스 강제를 설계 제약으로 못 박고, 마일스톤마다 저사양 실기로 검증한다.
- **오프라인 모드의 세이브 충돌**: 로컬/원격 세이브 충돌 해소 정책이 필요하다. M4(온라인 개방)에서 다루며, 그 전까지는 "가능하도록 경계를 긋는 것"까지만 한다.

## 4. 아트 파이프라인

### 4.1 문제 인식

1인 개발의 실제 병목은 코드가 아니라 아트다. RPG Maker가 살아남은 이유는 RTP(번들 에셋)와 배치식 맵 에디터를 제공하기 때문이다. A안에서 이를 어떻게 대체하는지가 이 섹션의 주제다.

**맵 제작 워크플로는 유지된다.** Tiled 또는 LDtk가 RPG Maker의 맵 에디터와 동일한 역할을 한다. 타일셋 PNG를 불러와 그리드에 칠하고 오브젝트를 배치한 뒤 JSON으로 내보내면 Phaser가 그대로 읽는다. LDtk는 규칙 기반 오토타일도 지원한다. 둘 다 무료다. **잃는 것은 에디터가 아니라 번들된 RTP 에셋뿐이다.**

**RTP 손실은 제한적이다.** RPG Maker로 만든 상업 게임 대부분이 RTP를 쓰지 않고 별도 에셋 팩을 구매한다. 그리고 같은 팩이라도 판매처에 따라 라이선스가 다르다 — Steam/RPG Maker 스토어 판은 "RPG Maker 전용" 라이선스, **itch.io 판은 엔진 무관 오픈 라이선스인 경우가 많고**, Humble Bundle 판은 일반 라이선스다. 따라서 **에셋은 itch.io에서 구매한다.** RPG Maker에 묶이는 것은 카도카와 자체 RTP와 일부 공식 DLC뿐이다.

### 4.2 스타일 계약

이 게임은 **가로 화면 전용**이다. 온스크린 컨트롤러를 좌우로 나눠 배치하려면 가로가 전제이며, 안드로이드 매니페스트에서 `sensorLandscape` 로 고정한다.

| 영역 | 스타일 | 규격 |
|---|---|---|
| 맵, 캐릭터, 몬스터, 채집 노드 | 픽셀아트 | **32×32 그리드 기준** |
| 인벤토리·제작·강화·거래소 UI | CSS (이미지 0장) | — |
| 아이템 아이콘 | 픽셀아트 | 32×32 |
| 인터페이스 기호 (닫기·정렬·탭·화살표) | SVG 벡터 | — |

**32×32 선정 근거:** 기준은 고정 해상도가 아니라 **짧은 축에 보이는 타일 수**다. 모바일 가로 화면의 논리 세로는 대략 360이므로 32×32면 **세로 11타일**이 보여 시야가 확보된다. 48×48이면 7타일에 그쳐 답답하다. 또한 Pipoya(무료)와 finalbossblues(유료, 엔진 무관 라이선스)가 타일셋·캐릭터·몬스터·아이콘을 모두 32×32로 제공하므로 하나의 생태계에서 일관되게 조달할 수 있다.

**가로폭은 고정값으로 적지 않는다.** 캔버스를 화면 크기에 그대로 맞추는(Phaser `Scale.RESIZE`) 방식이라 논리 가로폭이 기기 화면비마다 달라진다. 레터박스(검은 띠) 없이 화면을 꽉 채우는 대가이며, 세로 타일 수는 어느 기기에서나 11로 일정하다. **그래서 UI 요소의 위치를 월드 좌표로 잡지 않는다** — 상단 바와 온스크린 컨트롤러는 DOM 으로 만들어 CSS 픽셀에 배치한다.

**16×16 에셋 혼용 규칙**

채집·제작 장르는 16×16 에셋 풀이 더 두껍다. 좋은 16×16 소재를 발견하면 사용하되 다음 규칙을 지킨다.

> **16×16 에셋을 32×32 타일 크기로 확대하지 않는다.** 게임 전체가 배율 N으로 렌더링될 때 16×16 스프라이트도 동일한 배율 N으로 그린다. 화면상 반 타일 크기를 차지하지만 **아트 픽셀 밀도가 32×32 에셋과 정확히 일치**하여 자연스럽게 섞인다. 반대로 2배 확대해 타일을 채우면 픽셀이 두 배로 굵어져 즉시 이질감이 발생한다.

따라서 16×16 에셋은 **소품**(약초, 광석 조각, 도구, 장식물)으로 사용하고, 바닥 타일과 캐릭터는 32×32로 유지한다.

### 4.3 팔레트 통일 (혼합 스타일의 핵심 규칙)

픽셀 타일셋 팩에서 색을 추출해 CSS 변수로 고정하고, **UI와 아이콘은 그 팔레트만 사용한다.** 형태가 달라도 색이 같으면 하나의 게임으로 보인다. 팔레트가 어긋나면 아무리 품질이 좋아도 따로 논다.

```
apps/client/src/styles/tokens.css
  ← 픽셀 팩에서 추출한 팔레트가 유일한 색 출처
    UI, 아이콘, 이펙트 전부 여기서만 색을 가져온다
```

### 4.4 픽셀 선명도

`image-rendering: pixelated` + **정수 배율 스케일만 허용.** 1.5배 같은 소수 배율은 픽셀을 뭉개뜨린다. 기기 해상도에 따라 2x/3x/4x 중 하나를 선택하는 로직을 둔다.

### 4.5 아이템 아이콘 — 물량 문제의 해법

아이콘은 용도에 따라 두 소스로 분리한다.

| 용도 | 소스 | 근거 |
|---|---|---|
| **아이템 아이콘** (인벤토리·제작·거래소) | [finalbossblues 1000+ Fantasy RPG Icons](https://finalbossblues.itch.io/icons) — $6, 1,000개 이상, 32×32, 상업 이용 가능, **엔진 제한 없음, 크레딧 불필요** | 인벤토리 아이템은 UI 장식이 아니라 게임 콘텐츠다. 맵과 동일한 픽셀 스타일이어야 이질감이 없다 |
| **인터페이스 기호** (닫기·정렬·탭·화살표) | [game-icons.net](https://game-icons.net/) — 4,180개 SVG, CC BY 3.0 (크레딧 의무) 또는 CSS | 순수 UI 요소이므로 벡터가 적합 |

**「형태 × 재질 색상」 조합 생성은 픽셀아트에서도 그대로 성립한다.** 캔버스 팔레트 스왑은 픽셀아트의 표준 기법이며, 색상 램프를 명시적으로 정의할 수 있어 SVG 필터보다 결과가 정밀하다.

- **재질을 색상으로**: 동일 실루엣 + 팔레트 치환 → 구리/철/강철/미스릴/오리하르콘 = 아이콘 1장으로 5종
- **희귀도를 CSS로**: 테두리 광택, 배경 그라데이션, 파티클 → 이미지 추가 0장
- **강화 수치·세트 마크**: 오버레이

아이콘 200장 × 재질 6단계 × 희귀도 5등급 = 시각적으로 구분되는 6,000종을 이미지 200장으로 커버한다.

### 4.6 라이선스 관리

**① 팩 추가 전 확인 항목**

itch.io의 "Free" 표시는 자유 이용을 의미하지 않는다. 인기 팩 상당수가 **무료판은 비상업 전용, 상업 이용은 유료판**이라는 이중 라이선스를 사용한다 (Sprout Lands, Mystic Woods 등). 팩을 추가할 때마다 다음을 확인한다:

- [ ] 상업 이용이 가능한가 (무료판/유료판 구분 확인)
- [ ] 엔진 제한이 없는가 ("RPG Maker 전용" 표기 확인)
- [ ] 편집·개변이 허용되는가
- [ ] 크레딧 표기가 의무인가
- [ ] 재배포 조항 — 리포지토리 업로드 가능 여부

**동일 팩이라도 판매처에 따라 라이선스가 다르다.** finalbossblues 계열은 itch.io 판이 엔진 무관, RPG Maker 공식 스토어 판이 RPG Maker 전용이다. **에셋은 itch.io에서 구매한다.**

**② 에셋은 버전 관리에서 제외한다**

- `assets/CREDITS.md` 에는 **어느 팩을 어디서 구매했는지만** 기록해 커밋한다. 이것만으로 다른 환경에서 재구성이 가능하다

## 5. 게임 시스템

### 5.1 핵심 루프

```
채집 ──→ 재료 ──→ 제작 ──→ 장비/도구 ──→ 강화 ──→ 더 좋은 도구
  ↑                                                    │
  └──────── 더 높은 등급 노드에 접근 가능 ←─────────────┘
```

전투는 이 루프의 **바깥**에 있다. 재료 조달 수단이자 장비 드롭원이며, 주된 시간 소비처가 아니다.

### 5.2 시스템 목록

| 시스템 | 설계 |
|---|---|
| **생활기술** | 채집계(광물·벌목·약초·낚시 등) + 제작계(대장·재봉·연금 등). 각각 레벨 + 경험치. 도구 등급이 접근 가능한 노드를 제한 |
| **채집** | 맵에 노드 배치 → 상호작용 → 서버 판정 → 쿨다운 후 리스폰. 성공률 = f(숙련도, 도구, 노드 난이도) |
| **제작** | 레시피 = 재료 + 필요 숙련도 + 성공률. 실패 시 재료 일부 손실 |
| **강화** | 장비 +N. 성공/실패/하락/파괴. 이 게임의 주된 도파민 장치 |
| **전투** | **자동 턴제.** 요청 1회 → 서버가 전투 전체 판정 → 로그 + 드롭 반환. 클라는 로그를 애니메이션으로 재생 |
| **펫·용병** | 자동 채집 보조. 오프라인 진행의 출발점 |
| **장비** | 형태 × 재질 × 접두사 조합 생성 (5.3 참조) |

**전투를 자동 턴제로 두는 근거:** ① 서버 판정이 요청-응답 1회로 종료되어 구조가 단순하다 ② 모바일 조작에 적합하다 ③ v2에서 파티 보스를 도입할 때 "같은 전투 세션에 2인"으로 확장하면 되므로 재작성이 없다.

### 5.3 아이템 생성 규칙

아이템을 개별 정의하지 않고 조합으로 생성한다. 아트 제약과 데이터 물량 문제를 동시에 해결하는 구조다.

```
아이템 = 형태 × 재질 × 접두사
        (검·도끼·곡괭이)  (구리·철·미스릴)  (날카로운·견고한)

아이콘 → 형태 SVG + 재질 색상, 자동 조합
이름   → "날카로운 미스릴 곡괭이", 자동 생성
스탯   → 형태 기본값 × 재질 배수 × 접두사 보정, 자동 계산
```

형태 20개 + 재질 8개 + 접두사 10개 = **1,600종의 장비**가 아이콘 20장, 데이터 38행에서 생성된다.

## 6. 데이터 모델 및 파이프라인

### 6.1 `packages/data`

CSV를 입력받아 검증하고 타입 있는 JSON을 출력한다.

| 파일 | 내용 |
|---|---|
| `shapes.csv` | 형태 (검·도끼·곡괭이 등) → 기본 스탯, 아이콘 SVG 경로 |
| `materials.csv` | 재질 (구리·철·미스릴 등) → 스탯 배수, 색상 코드 |
| `affixes.csv` | 접두사 → 스탯 보정 |
| `recipes.csv` | 레시피 → 재료, 필요 숙련도, 성공률 |
| `skills.csv` | 생활기술 → 레벨 곡선, 해금 조건 |
| `nodes.csv` | 채집 노드 → 산출물, 난이도, 리스폰 주기 |
| `monsters.csv` / `drops.csv` | 몬스터 및 드롭 테이블 |

빌드 스크립트가 **참조 무결성을 검증**한다: 존재하지 않는 아이템 ID를 참조하는 레시피, 도달 불가능한 숙련도 요구치, 순환 레시피 등. 수천 행 CSV의 오타를 런타임이 아닌 빌드 타임에 잡는다.

### 6.2 밸런스 시뮬레이터

노가다 게임의 밸런스를 수작업으로 맞추는 것은 불가능하다. `packages/shared`의 공식을 그대로 import 하여 가상 플레이 세션을 시뮬레이션하는 스크립트를 둔다.

출력 예:
- 광부 숙련 1→50까지 실제 소요 시간
- 미스릴 곡괭이 획득까지 필요한 채집 횟수
- +10 강화 기대 비용 (파괴 확률 반영)

**공식이 `shared`에 하나뿐이므로 시뮬레이터가 실제 게임과 100% 동일한 계산을 수행한다.**

### 6.3 DB 스키마 요점

**아이템을 두 종류로 분리한다.**

| 종류 | 대상 | 저장 방식 |
|---|---|---|
| 스택형 | 재료·소모품 | `(player_id, item_code, count)` 한 행 |
| 인스턴스형 | 장비 | 고유 ID + 강화수치 + 접두사, 개별 행 |

강화 수치가 붙는 순간 개별 정체성이 생겨 스택이 불가능하다. 이 구분을 나중에 도입하려면 인벤토리·거래소·우편을 전부 재작성해야 하므로 **초기부터 분리해야 하는 결정**이다.

주요 테이블: `players`, `characters`, `inventory_stacks`, `item_instances`, `skill_progress`, `market_listings`, `mail`

거래소는 **원장(ledger) 방식**으로 구현한다. 아이템 이동을 삭제·생성이 아니라 소유권 이전 기록으로 남긴다. 아이템 복사 버그 발생 시 추적 가능성이 확보된다.

## 7. 마일스톤

주 15~20시간(평일 저녁 + 주말) 기준. 풀타임 시 약 절반.

> **구현 계획의 범위:** 이 문서는 프로젝트 전체(7~10개월)를 다루므로 하나의 구현 계획으로 소화할 수 없다. **첫 구현 계획은 M0 + M1까지만 다룬다.** M1은 "계속할지 판단하는 관문"이므로, 그 결과에 따라 이후 마일스톤의 내용 자체가 바뀔 수 있다. M1 통과 후 M2용 계획을 별도로 작성한다.

### M0 · 기반 세팅 — 1~2주

모노레포 구성, Phaser + React 통합, 서버 스캐폴딩, 타일맵 로드 및 캐릭터 이동. 에셋 팩 1개 구매 후 팔레트 추출.

**필수 관문: 안드로이드 빌드 1회 성공.** 게임이 비어 있는 상태에서 Capacitor 빌드를 통과시켜야 한다. 나중으로 미루면 "웹에선 되는데 실기에선 안 되는" 문제가 누적된 뒤 한꺼번에 발생한다. 지금은 하루, 6개월 뒤에는 2주가 걸린다.

### M1 · 코어 루프 수직 슬라이스 — 4~6주

맵 1개, 채집 노드 3종, **생활기술 2종 — 채집계 「광부」 + 제작계 「대장」**, 제작 레시피 10개, 인벤토리, 저장. 서버는 localhost.
**채집 → 재료 → 제작 → 더 좋은 곡괭이 → 더 좋은 채집**이 한 바퀴 돌아야 한다.

광부/대장 조합을 고르는 이유는 이 둘만으로 핵심 루프가 자기완결적으로 닫히기 때문이다. 광부가 캔 광석으로 대장이 곡괭이를 만들고, 그 곡괭이로 더 높은 등급 광맥에 접근한다. 다른 조합(예: 약초+연금)은 산출물이 소모품이라 루프가 닫히지 않아 재미 검증에 부적합하다.

**프로젝트 전체에서 가장 중요한 판정 지점.** 여기서 재미없으면 물량을 100배로 늘려도 재미없다. M1 완료 후 반드시 며칠 직접 플레이하고 계속할지 판단한다. 지인 2~3명에게 로컬 빌드를 보여주는 것도 이 시점에 한다.

### M2 · 시스템 확장 — 6~8주

장비(형태×재질×접두사), 강화, 자동 턴제 전투 + 드롭, 생활기술 8~10종, 밸런스 시뮬레이터.
**레시피 트리의 구조 설계를 이 단계에서 끝낸다** (M3 리스크 완화).

### M3 · 콘텐츠 물량 — 6~10주

맵 확장, 레시피 트리 완성, 아이템 수백 종, 펫·용병 자동채집.

### M4 · 온라인 개방 — 6~8주

계정·인증, 원격 서버 전환, presence + 채팅, 거래소, 레이트 리밋, 치팅 대응, 로컬/원격 세이브 충돌 정책.

### M5 · 출시 준비 — 4주+

튜토리얼·온보딩, 크레딧, 개인정보처리방침(온라인이므로 필수), 플레이스토어 등록.

**합계: 약 7~10개월**

### AI 보조의 적용 범위

AI는 보일러플레이트, API 구현, 데이터 변환, 리팩터링, 테스트 작성에 강하다 — M0·M2·M4의 상당 부분이다. 반면 **레시피 트리 설계, 밸런스 감각, 아트 디렉션, "이게 재미있는가" 판단**에는 거의 기여하지 못한다. 프로젝트의 성패는 후자에 달려 있으므로 **개발자의 시간을 M1과 M3에 집중 배분한다.**

## 9. 테스트 전략

게임의 핵심 로직이 순수 함수이므로 테스트에 유리한 구조다.

| **경제 불변식** | **최우선.** "거래 전후 아이템 총량 보존", "골드가 생성·소멸되지 않음", "동시에 같은 매물을 두 명이 구매하면 하나만 성공". 아이템 복사 버그는 이것 외에 잡을 방법이 없으며, 온라인 경제가 무너지면 복구 불가능하다. **M4 이전에 반드시 갖춘다** |
| 밸런스 시뮬레이터 | 회귀 테스트로 활용. 공식 수정 후 "광부 1→50 소요 시간"이 급변하면 CI 경고 |
| 클라 UI | **자동화하지 않는다.** 비용 대비 효익이 낮다. 수동 테스트로 충분 |

## 11-1. M1 구현이 이 문서와 다른 지점 (2026-08-02, M0+M1 기반 완료 후 기록)

M0(Task 1~4) 구현과 브랜치 전체 리뷰에서 드러난, **의도적으로 미룬 구조 결정**들이다.
M2 계획을 쓸 때 이 표를 먼저 읽는다. 지금 고치지 않은 이유와 나중에 치를 비용을 함께 적는다.

| 지점 | 현재 M1 구현 | 이 문서가 말하는 최종형 | 미룬 이유 / 나중 비용 |
|---|---|---|---|
| 아이템 정의 | `items.csv` 에 아이템 1종 = 1행, `ItemDef.icon` 은 문자열 하나 | §5.3 형태 × 재질 × 접두사 조합 생성 (`shapes/materials/affixes.csv`) | M1은 13종뿐이라 조합 엔진이 과잉. **M2에서 `items.csv` 와 `ItemDef` 를 통째로 교체**하고, 이름·아이콘·스탯 파생 규칙이 `packages/shared` 에 새로 들어간다 |
| `ItemInstance` | `instanceId` + `itemId` + `enhanceLevel` | §6.3 은 접두사(affix)까지 포함한다 | 필드 추가는 지금 공짜이나 M1에 소비처가 없다. 영속 계층이 생긴 뒤 추가하면 마이그레이션이 된다 |
| `equipped` | `Partial<Record<SkillId, string>>` — 생활기술을 슬롯 키로 씀 | 무기·방어구는 생활기술에 속하지 않는다 | M1은 기술당 도구 1개라 정확하다. **장비 종류가 늘면 키 공간을 바꿔야 한다** |
| `instances` | 배열 | — | `instanceId` 조회가 강화·거래소·우편의 주 연산인데 배열은 전부 O(n)이다. M1 규모에선 무의미하나 M2에서 레코드로 바꾸는 편이 낫다 |
| 통신 스키마 | zod 스키마가 아직 없다. 응답 타입은 `apps/server` 안에 있다 | §3.2 는 `packages/shared` 를 스키마의 집으로 지정 | Task 7~9에서 결정할 사항. 지금 구조면 `apps/client → apps/server` 가 구조적 의존이 되고 `packages/data` 는 재사용할 수 없는 층 아래 놓인다. **Task 8 착수 시 의식적으로 정할 것** |

### 남아 있는 알려진 Minor (차단 요소 아님)

- `parseCsv` 의 칸 수 불일치 오류가 파일명 없이 줄 번호만 낸다 (`nodes.csv` 와 `recipes.csv` 의 같은 줄이 구분되지 않음)
- `loadGameData()` 신선도 검사가 id 집합만 비교한다. CSV 값만 바꾸고 재빌드하지 않은 채 `vitest` 를 직접 돌리면 낡은 값이 통과한다 (루트 스크립트는 항상 재빌드하므로 실사용 경로는 안전)
- `loadGameData()` 반환 타입이 `Readonly<GameData>` 가 아니라 `GameData` 다. 변경 방지는 런타임 동결로만 이뤄진다
- 헬스 체크 테스트가 프로덕션과 같은 방식으로 개수를 계산한다 (같은 버그를 양쪽이 공유하면 잡지 못함)
- `pnpm install` 이 `Ignored build scripts: esbuild` 경고를 낸다
- `PORT` 가 빈 문자열이면 0번 포트에 바인딩된다
- CORS 가 무조건 `origin: true` 다 — **Task 7에서 플레이어 식별이 들어오기 전에 환경별로 좁혀야 한다**
- README 와 CI 가 없다. `git clone && pnpm install && pnpm test` 가 개발자 1인의 Windows 장비에서만 검증돼 있다
