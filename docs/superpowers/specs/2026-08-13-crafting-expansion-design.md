# 제작 확장 설계 — 세 계열이 자기 손을 갖는다

**날짜:** 2026-08-13
**상태:** 깨끗한 세션 평가 3렌즈 반영 완료 — **§6-앞이 규범**(앞 절과 충돌하면 §6-앞이 이긴다)
**사용자 지시:** "제작의 경우에는 광산채굴을 통한 작업 위주로 구현하였는데 얼음,
나무, 허브는 제작과 관련한 기능이 존재하지 않아. 이부분을 보강해."

**진단:** 레시피 17종 중 **광물 사슬이 13종**(주괴 4 + 도구 9)이고, 얼음·나무·허브
재료는 남의 레시피 부재료로만 쓰인다. 제작 패널의 카테고리도 `제련`·`도구` 둘뿐이라
**세 계열 플레이어는 캘 줄만 알고 만들 줄은 모른다.**

**원작 발굴(스크래치패드 recipes_parsed.txt, recipes_craft_660_780.txt, ul4_ladder.txt,
econ_recipes.txt, ce/ 덤프):**
- 원작 제작은 **두 층**이었다. ① **가공**(가공장인 NPC, 게이트 없음, 실패 없음,
  원료 100 → 정제품 1, 골드 손익 0 — 목적은 이득이 아니라 **부피 압축**)
  ② **조합**(조합 숙련 var22 게이트, **재료 전소** 실패, 포션·주문서·가루·장비 85종).
  광물만 세 번째 층(대장 숙련 var484 제련)을 더 가졌다.
- **초급 조합이 계열을 섞는다**: 힐링포션 = 허브5 + 라벤더1 + **얼음1**,
  허브티 = 허브10 + **찻잎1**, 해독제 = 허브12 + 라벤더3 + 세이지1 + **깨끗한얼음1**.
  세 계열이 서로를 먹인다 — 우리 미스릴 사슬과 같은 정신의 원작 근거다.
- **강화 사다리(UL4)가 세 계열 재료의 최대 소비처였다**: +1~3 목재 → +4~6 허브
  → +7~9 찻잎 → +10~12 아로마 → +13~15 얼음의보석 → +16~18 생명의열매
  (최대 830개). 생명의열매는 조합 레시피가 하나도 없고 **오직 강화에서만** 쓰였다.
- 나무의 가구·활·요리, 얼음 전용 무기 사슬은 **원작에 없다**(지어내지 않는다).

---

## 1. 목표

얼음·나무·허브에 각자의 제작이 생긴다. 캐기만 하던 재료가 **정제되어** 값이 되고,
그 정제품이 **도구를 강화해** 다음 채집을 빠르게 한다. 제작 패널에 세 계열의
카테고리가 선다.

## 2. 결정 1 — 정제(가공) 층: 세 계열 각 3종, 총 9 레시피

원작의 가공장인을 레시피로 옮긴다. 다만 **NPC 창구가 아니라 제작 패널 안**이다 —
우리에겐 이미 좌 목록·우 상세·제작 버튼이 있고, 상점(NPC 창구)과 제작(패널)의
분업이 이미 서 있다. 새 창구를 만드는 것은 시스템을 늘리기만 한다.

| 카테고리 | 레시피 | 입력 | 산출 | requiredSkill |
|---|---|---|---|---|
| **정제** | 얼음 덩이 `ice_block` | 얼음 조각×20 | ×1 | 0 |
| | 맑은 얼음 덩이 `pure_ice_block` | 맑은 얼음×15 + 얼음 덩이×1 | ×1 | 1,200 |
| | 얼음 결정 덩이 `crystal_block` | 얼음 결정×10 + 맑은 얼음 덩이×1 | ×1 | 6,000 |
| | 압축 목재 `compressed_log` | 무른 통나무×20 | ×1 | 0 |
| | 고압축 목재 `dense_log` | 단단한 통나무×15 + 압축 목재×1 | ×1 | 1,200 |
| | 농축 잎물 `leaf_extract` | 찻잎×10 + 금빛 잎×3 + 고압축 목재×1 | ×1 | 6,000 |
| | 허브 농축액 `herb_extract` | 흔한 약초×20 | ×1 | 0 |
| | 라벤더 향유 `lavender_oil` | 라벤더×15 + 라임×5 + 허브 농축액×1 | ×1 | 1,200 |
| | 세이지 정수 `sage_essence` | 세이지×10 + 귀한 약초×3 + 라벤더 향유×1 | ×1 | 6,000 |

- **원작 정신 보존**: 정제는 **부피 압축**이지 이득이 아니다. 가격은 경제 아크의
  불변식(`산출 매도 ≤ 입력 매도합`)을 그대로 지키며, **입력 매도합의 0.8배**로
  둔다(원작 제련 비율대와 같은 자리). 팔아서 이득 보는 길이 아니라, **다음 층의
  재료**라는 것이 존재 이유다.
- 각 계열의 **1단은 requiredSkill 0** — 세 계열 플레이어가 첫날부터 만들 것이 있다
  (부트스트랩 검증이 스킬당 0-레시피를 이미 요구한다).
- 사다리 안에서 하위 정제품이 상위의 입력이 된다 — 죽은 재료 13종 중 **9종이
  여기서 제작으로 구제된다**(나머지는 판매로 이미 구제됨).

## 3. 결정 2 — 강화가 정제품을 먹는다 (원작 UL4 사다리)

지금 강화는 **같은 도구 예비 1개**만 먹는다. 원작처럼 **계열 재료를 함께** 먹게 한다.

| 강화 단계 | 예비 도구 | 추가 재료(그 도구 기술의 계열) |
|---|---|---|
| +1 | 1개 | 1단 정제품 ×1 |
| +2 | 1개 | 1단 정제품 ×3 |
| +3 | 1개 | 2단 정제품 ×1 |
| +4 | 1개 | 2단 정제품 ×3 |
| +5 | 1개 | 3단 정제품 ×2 |

- 계열 대응: 얼음 도구 → 얼음 정제품, 나무 → 나무, 허브 → 허브, **광물 → 주괴**
  (구리/은/금 주괴가 그 자리에 들어간다 — 광물도 같은 규칙을 받는다),
  **조합(망치) → 세 계열 1단 정제품 각 1**(조합은 계열이 없으니 셋을 다 먹는다 —
  원작의 "서로를 먹이는" 자리).
- 데이터가 소유한다: `enhance_costs.csv (skill, level, itemId, count)`. 코드에
  숫자를 적지 않는다.
- 서버 `performEnhance` 가 재료를 검사·소모한다. 새 오류 코드
  `missing_enhance_materials`. **강화는 실패하지 않는다**(현행 유지 — 도박 강화는 훅).
- 이로써 정제품에 **골드가 아닌 용도**가 생긴다: 강화는 채집 간격을 줄이므로
  "재료 → 정제 → 강화 → 더 빠른 채집"이 닫힌 고리가 된다.

## 4. 결정 3 — 계열별 제작 숙련을 만들지 않는다

원작도 조합은 **숙련 하나**(var22)였다(대장 제련만 따로). 계열별로 쪼개면 SkillId·
이정표·화면·검증이 전부 늘어나는데, 얻는 것은 "얼음 제작을 많이 하면 얼음 제작이
는다"는 동어반복뿐이다. **`crafting` 하나를 유지한다.**

## 5. 결정 4 — 화면: 카테고리가 넷이 된다

제작 패널의 좌 목록에 `정제`가 추가돼 `제련 · 정제 · 도구` 셋(카테고리 순서 = CSV
행 순서)이 된다. 정제 9종이 한 카테고리에 들어가면 좌 목록이 길어지므로,
**카테고리 접기/펼치기는 넣지 않는다**(스크롤로 충분하다 — 812×375 에서 목록은
이미 스크롤이고, 접기는 상태를 하나 더 만든다).

## 6-앞. 깨끗한 세션 평가 반영 (규범 — 앞 절과 충돌하면 이 절이 이긴다)

평가 셋이 같은 급소를 찔렀다: **§2 의 정제 9종은 원작을 인용해 놓고 원작의 성질을
하나도 남기지 않은 대칭 껍데기이고, 그 유일한 소비처인 강화는 몇 시간 만에 수요가
끝난다.** 실측: 평생 필요량이 1단 30·2단 18·3단 6인데, 3단 문을 여는 데만 정제
**400회 성공**이 필요하다(96% 낭비). 게다가 정제해서 팔면 기대 −33.5%라 원료를 그냥
파는 것에 **항상 지배당한다** — 정제는 함정이었다.

**A. 얼음의 정체는 날씨 가루다 (치명 — 이 아크에서 가장 값진 발견)**

1. 원작 얼음 계열의 조합은 정제품이 아니라 **날씨 가루 9종**이었다(눈·비·폭풍우
   × 약·중·강, 게이트 var22 50/500/2500, 입력 `얼음10+깨끗한얼음5` 식). 효과는
   전투가 아니라 **연출**(`SetWeatherEffects`)이라, **전투도 HP도 없는 우리 게임에
   손대지 않고 그대로 옮길 수 있는 유일한 원작 소비재**다.
2. 우리 코드에는 그 자리가 **이미 파여 있다**: `dialogue.ts` 의
   `{ name: 'weather', supplied: false }`, `facts.ts` 의 "공급자가 없다고 선언된
   사실은 넣지 않는다", 그리고 `채집장노인.dlg` 의 `@greet weather=rain` 이 잠든 채
   빌드가 매번 "대사 N줄이 weather 를 기다린다"를 찍는다.
3. → **얼음 계열의 제작은 날씨 가루다.** 소모품이라 **수요가 무한**하고(정제
   수요 붕괴를 직접 해결), 골드 싱크이며, 잠든 대사를 깨우고, 얼음에만 있는
   정체를 준다. v1 범위: **눈 가루·비 가루 각 약/중 4종**.
4. **날씨는 개인 상태다**(전역이면 남의 세계를 바꾸는 권한이 생긴다):
   `PlayerState.weather: { kind, untilMs } | null`(`.default(null)`). 서버가
   `POST /api/use` 로 판정하고, `facts` 가 그것을 `weather` 사실로 공급한다.
   만료는 시각 비교(저장할 타이머 없음 — 우리 NPC 일과와 같은 자세).
   클라이언트는 하늘 연출로 표면화한다.

**B. 나무·허브는 정제 사슬을 갖되, 수요가 영구해야 한다**

5. 정제는 **나무 3종 · 허브 3종**만 남긴다(얼음은 A 로 대체, 광물은 이미 주괴가
   그 자리다 — 계열마다 **다른 모양**이 되는 것이 대칭 껍데기보다 낫다).
6. **미스릴 도구 레시피가 raw 재료 대신 3단 정제품을 먹게 바꾼다**
   (`golden_fruit|millennium_leaf|aroma_herb` → `농축 잎물|세이지 정수`).
   그러면 정제품 수요가 도구 사슬에 **영구히** 붙고, 계열이 서로를 먹는 원작
   정신이 도구 쪽에서 유지된다.
7. **가격비는 1.0**(원작 가공은 차익 정확히 1.00이었다), **baseChance 0.95**
   (원작 가공은 실패가 없었다 — 우리 검증이 `0<chance<1` 을 강제하므로 0.95가
   "사실상 무실패"의 표현이다). 0.8 은 원작 근거가 없었다.
   부피 압축이 우리에게 값어치 0인 이유도 함께 적는다(스택 상한이 없다).
8. **skillGain 명시**(이 값 하나가 아크 전체 밸런스를 정한다 — 조합 숙련 속도가
   재료 드랍 브라켓과 커플링된다): 1단 `10,20` · 2단 `25,40` · 3단 `40,70`
   (주괴와 같은 자리).

**C. 문턱은 조합이 아니라 그 계열 채집 숙련이 연다**

9. 같은 레시피가 플레이 순서에 따라 0.2분과 11시간을 오간다 — 진짜 문턱은
   조합 숙련이 아니라 **그 계열 채집 브라켓**이기 때문이다.
   → `recipes.csv` 에 `gateSkill,gateValue` 를 추가하고 `canCraft` 가 둘 다 본다.
   정제·가루의 `requiredSkill`(조합)은 **0**으로 두고 계열 채집 숙련으로만 막는다.
   그러면 **이정표가 필요 없어지고**(`requiredSkill>0` 레시피만 이정표를 요구한다)
   목록방도 안 늘어난다 — 평가가 지적한 "빌드가 반드시 빨개진다"가 함께 해소된다.
   화면은 두 숫자를 다 말한다(우리 "요구치를 숫자로 말하는 문" 그대로).
10. 게이트 값: 1단 계열 채집 1,000 · 2단 10,000 · 3단 50,000(날씨 가루는
    약 1,000 · 중 10,000).

**D. 강화는 원작 UL4 를 제대로 옮긴다 (§3 을 대체)**

11. UL4 를 세 군데 오독했다: ① 먹는 것은 **원재료**다(정제품이 아니다)
    ② **계열별이 아니라 단계별 회전**이다(한 무기가 나무→허브→찻잎→아로마→
    얼음→생명의열매를 차례로 요구한다 — UL4 야말로 "서로를 먹이는" 장치인데
    §3 은 그것을 계열 대응으로 뒤집어 그 성질을 버렸다) ③ **골드를 함께 먹는다**.
    → 강화 비용 = **단계마다 다른 계열의 원재료 + 골드**. 계열 회전으로 모든
    도구가 네 계열을 다 요구하고, 골드는 우리의 두 번째 싱크가 된다.
12. **도구 티어를 비용 키에 넣는다** — 같은 표가 구리에선 비용의 99.9%,
    미스릴에선 0.5%였다. `enhance_costs.csv (toolTier, level, itemId, count, gold)`.
13. **`enhance_costs` 는 GameData 에 싣는다**(확률표와 달리 화면이 요구량을 적어야
    한다). 그 결과 `performEnhance` 가 `items`·`costs` 를 받고 enhance 라우트가
    GameData 를 받게 된다 — 지금 "GameData 를 받지 않는 유일한 라우트"라는 그
    파일의 주석도 함께 고친다. 새 오류 코드 `missing_enhance_materials`·
    `not_enough_gold`.
14. **망치 강화에 제작 간격 절감을 붙인다**(지금 제작 간격은 강화를 무시한다) —
    망치 +5 가 세 계열을 먹으면서 보상이 성공률 +1.5%p 뿐이라 아무도 안 한다.
    간격이 짧아지면 정제 노가다 자체가 빨라져 B 의 수요도 함께 산다.

**E. 빠진 배관**

15. 새 아이템 아이콘(정제 6 + 가루 4 = 10종)은 **컨트롤러가 대조 시트로 확정**해
    계획에 박는다. CREDITS 표·복원 heredoc·유일성 테스트 절차 그대로.
16. `gateSkill/gateValue`·`enhance_costs`·`weather` 각각의 검증을 새로 적는다
    (없는 기술·음수·단계 연속성·없는 아이템·계열 누락·만료 시각 단조성).
17. 정제품·가루의 `skill` 은 그 계열 — 그 계열 상점이 사 준다(죽은 아이템 검사
    통과). 가루는 소모품이라 **팔면 손해**가 자연스럽다(입력 원가 > 산출 매도).

## 6. 무엇을 안 하는가 (훅만)

- **포션·소비재** — 우리에겐 HP·허기·전투가 없어서 원작 포션을 그대로 옮기면
  즉시 죽은 아이템이 된다. 소비 효과(일시 버프)는 **버프 시스템과 한 몸**이라
  별도 아크. 그때 원작의 포션 사다리(힐링→허브티→해독제→…→신의기운)를 그대로
  쓸 수 있다 — 레시피는 이미 발굴해 뒀다.
- 주문서·가루(날씨·포탈), 장비(반지·천관), 가공장인 NPC 창구, 10개씩 제작,
  계열별 제작 숙련, 강화 실패·도박, 정제품 되사기 상점.

## 7. 성공 기준

1. 얼음·나무·허브만 캔 플레이어가 제작 패널에서 **자기 계열 정제품을 만들 수 있다**
   (각 계열 1단은 조합 숙련 0에서 열린다).
2. 정제 사다리 3단이 각 계열에서 실제로 이어진다(1단이 2단의 입력, 2단이 3단의 입력).
3. 도구 강화에 **정제품이 실제로 소모**된다 — 재료가 모자라면 서버가 거절하고,
   화면이 무엇이 얼마나 필요한지 말한다.
4. 죽은 재료 13종 중 9종이 정제 입력으로 쓰인다(빌드가 세는 것으로 증명).
5. 경제 불변식 유지: 새 레시피 전부 `산출 매도 ≤ 입력 매도합`, 왕복 손해.
6. 기존 세이브 무이행(강화 재료 요구는 **다음 강화부터** 적용 — 이미 강화한 도구는
   그대로).
7. `pnpm data:build && pnpm test && pnpm typecheck` 초록, 판정은 전부 서버.
