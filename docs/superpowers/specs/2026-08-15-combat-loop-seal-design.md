# 전투 루프 봉합 설계 (아크 D)

> **For agentic workers:** 이 스펙은 아크 C(전투)가 배포된 직후의 봉합 아크다.
> 새 콘텐츠가 아니라 **이미 배포된 루프의 새는 곳 다섯을 잇는 배선**이다.

## 0. 왜 이 아크인가 (깨끗한 세션 추천 + 실측)

전투가 배포됐지만 루프가 안 닫혀 있다:

1. **강화가 피해를 안 산다** — `swingDamage`(shared/combatState.ts)가 `enhanceLevel`
   을 참조하지 않는다. 강화 기계(UL4: 같은 도구의 예비 인스턴스 + 재료 + 골드)는
   이미 검을 먹을 수 있고, +5 = 예비 검 5자루 = **송곳니 60개**의 반복 수요가
   코드에 실재한다 — 그러나 +5 검이 +0 과 똑같이 때리므로 그 수요에 동기가 없다.
   §4 의 약속("송곳니 잉여는 검 강화 수요가 닫는다")에서 죽어 있는 것은 수요가
   아니라 **보상**이다.
2. **여관 회복 기계가 없다** — 값(500G)과 부등식(§6: 회복비 ≤ 자연 회복 대기
   5분의 벌이)은 `innPricing.test.ts` 가 결정해 뒀지만 상수가 테스트 안에만 있고
   기계가 없다. 죽으면 "5분 기다림"이 유일해서 §6 의 저울(여관 vs 대기)이 없다.
3. **예고 ≥ ε+700 이 기계 강제가 아니다** — 검사 3 은 700ms 만 본다. 700~1,699ms
   예고를 저작하면 예고 전체가 스미어(전 구간 확정 피격)가 되는데 빌드가 침묵한다.
4. **주장 좌표가 무상한이다** — claim (10⁹,10⁹) 첫 주장이 수락돼 lastClaim 에
   박히고, 이후 정직한 주장이 implausible_move 로 묶인다(전체 리뷰 재현 — 치터
   이득은 0이지만 자기 발 묶기가 가능하다).
5. **송곳니 판로(씨앗 ⑧)는 이 아크에서 열지 않는다 — 의식적 미룸.** 강화 수요
   60개(≈120처치 ≈ 40분+)가 당분간의 출구다. 판로는 사냥 전용 상점이 어울리고,
   그 상점은 방어구 사슬 아크(드랍 종류가 늘 때)의 몫이다. 지금 기존 상점의
   `isSellTarget`(계열 일치)에 전투 예외를 뚫으면 술어 하나가 둘로 갈라진다.

## 1. 강화 → 피해 (D1)

**식은 shared 하나** — `combatState.ts` 에:

```ts
/** 강화 +n 검의 회당 피해 — 기본 피해 + n (선형 +1). */
export function swingDamageOf(def: ItemDef, enhanceLevel: number): number {
  return (def.damage ?? UNARMED_COMBAT_DAMAGE) + enhanceLevel
}
```

- `swingDamage(player, items)` 는 `equippedToolInfo` 의 인스턴스에서 enhanceLevel
  을 꺼내 이 식을 부른다. 맨손은 기본 상수 그대로(강화가 없다).
- **선형 +1 인 이유**: 티어(승급)가 굵은 축, 강화가 가는 축 — 도구 루프의 규범
  그대로다. 구리 검 5 → +5 에 10. 들늑대(HP 8)는 +3 부터 1스윙이 된다: 첫 검의
  강화 사다리에 실제 문턱(2스윙→1스윙)이 하나 놓이고, 그 문턱은 화면(가방 피해
  숫자)이 말한다 — 요구치를 숫자로 말하는 문의 자리다.
- 화면: 가방 전투 칸의 `피해 N` 은 이 식을 부른다(`toolSpeedLabel` combat 분기 —
  def.damage 직접 읽기 은퇴). 제작·강화 요구 화면(enhanceCostModel)이 피해
  증가를 말하는지 확인하고, 안 말하면 "+1 피해" 한 줄을 더한다.
- 분-자: 강화는 부트스트랩(첫 검 3~8분) 밖이다 — combatBootstrap 무변경.

## 2. 여관 회복 (D2)

- **데이터**: `inns.csv` 한 행 — `speakerId,gold` → `여관안주인,500`.
  파서·검증(있는 화자인지, gold ≥ 1)·굽기(gamedata.json — 값은 화면이 문에
  적어야 하므로 숨은 문턱이 아니다).
- **서버**: `POST /api/inn` (innService.performRest) —
  ① gold < price → `not_enough_gold` ② `currentHp === COMBAT_MAX_HP` →
  `already_full`(회복할 것이 없는데 돈을 받으면 죽은 버튼의 서버판이다)
  ③ 수락: gold 차감, `combat.hp = COMBAT_MAX_HP`, `combat.lastHitAt = now`.
  근접 게이트는 상점과 같은 신뢰 모델(없음).
- **상수의 거처**(씨앗 ⑦ 종결): 값은 inns.csv 가 소유하고, `innPricing.test.ts`
  는 **구운 데이터에서 읽어** 부등식을 못박는다 — 테스트 안의 상수 사본 삭제.
- **화면**: 여관 안주인과 대화하면 대화 갈래에 `쉬어간다 (500G)` 가 뜬다 — 대화
  시스템의 기존 갈래 기계를 쓰되, 갈래가 서버 행동을 부르는 첫 사례면 상점 문법
  (대화 → 패널 버튼)을 따른다. 만혈이면 갈래 자체를 그리지 않는다(죽은 버튼
  금지). 피격 직후 밤 동선: 사냥터에서 죽음 → 마을 스폰 → 여관(9,14)까지 몇 걸음
  — §6 이 그린 그 동선이 처음으로 완성된다.

## 3. 예고 하한의 기계 강제 (D3)

- `monsterChecks.ts` 검사 3: `TELEGRAPH_MIN_MS = 700` 은 유지(반응 예산의 하한)
  하고, **새 하한 하나를 더한다**: `telegraphMs ≥ JUDGE_EPSILON_MS + 700`
  (shared 에서 import — ε 가 C7 재측정으로 줄면 하한도 따라 준다). 위반 문구는
  "예고 Nms — ε(1,000ms) 스미어를 빼면 안전한 예고가 [N−1000]ms 뿐이다. 하한
  1,700ms" 꼴로, 왜가 문장에 있어야 한다.
- **픽스처 연쇄를 수용한다**: monsterChecks.test 의 기본 공격(telegraphMs 700,
  1,100ms 간격 창)이 전부 새 하한에 걸리므로, 기본 픽스처를 예고 1,800ms·창 간격
  재배열로 손본다. 이 비용을 미루지 않는 이유: C6 데이터는 우연히 1,800 이었고,
  다음 몬스터 저작자가 700을 적는 순간 "예고를 보고 피한다"가 조용히 죽는다.
- 돌연변이: 출하 wolf 의 telegraphMs 를 1,000 으로 바꿔 빌드가 이 문구로 서는
  것을 확인하고 원복.

## 4. 주장 좌표 상한 (D4)

- `performFight` ②′(wrong_map 다음): claim 이 `data.maps[플레이어 맵]` 의
  폭·높이 밖이면 `implausible_move` 로 거절 — 맵 밖 칸은 걸을 수 없다는 것을
  서버가 확실히 안다(§2-3 의 "벽은 못 막지만 맵 밖은 막는다"). lastClaim 을
  적기 전이므로 자기 발 묶기가 원리적으로 사라진다.
- FightRequestSchema 는 그대로(비음수 정수) — 상한은 맵마다 달라 스키마가 아니라
  판정의 몫이다.

## 5. 검증·닫음 (D5)

- 관문 셋 + 돌연변이(각 태스크가 자기 것).
- 브라우저: 강화한 검의 피해 숫자(가방·플로트)와 1스윙 문턱, 여관 회복(골드
  차감·HP 만혈·만혈 시 갈래 없음), 죽음→여관 동선.
- 전체 브랜치 리뷰 → 푸시 → 미니PC health.sha 확인.
