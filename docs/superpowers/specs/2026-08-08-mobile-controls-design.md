# 모바일 조작과 상호작용 설계

**날짜:** 2026-08-08
**상태:** 서브에이전트 평가 반영 완료
**선행:** [숙련도 재설계](2026-08-03-proficiency-design.md), [세계 시각](2026-08-02-world-time-design.md)

---

## 1. 왜 지금 바꾸나

지금 게임은 **캐릭터를 탭해서 이동하고 노드를 탭해서 채집한다.** 이 방식은 버린다.

원작은 컨트롤러로 노드에 붙어서 상호작용 버튼을 반복해 누르는 게임이다. 그 감각이 이 게임의 정체성이다. 탭 방식은 세 가지를 동시에 망가뜨린다.

1. **노드에 "붙는다"는 개념이 사라진다.** 화면 반대편 노드도 탭 한 번이면 캔다. 위치가 의미를 잃는다.
2. **반복의 육체성이 사라진다.** 원작에서 채집은 손가락으로 버튼을 계속 누르는 행위였다.
3. **온라인으로 갈 길이 막힌다.** 자유 위치 + 임의 노드 지정은 서버가 검증할 수 없다. 한 화면에 여러 플레이어를 놓으려면 위치가 규칙이어야 한다.

---

## 2. 원작이 실제로 한 것

원작 APK 의 Ruby 스크립트와 이벤트 데이터를 직접 읽어 확인한 것만 **사실**로 적는다. 해석은 그렇다고 표시한다.

### 2.1 이동 — 확인됨

**순수 4방향 타일 이동.** `Game_Player` 는 RPG Maker XP 표준 스크립트와 100% 동일하고 `Input.dir4` 만 쓴다. `Input.dir8` 호출은 전체 스크립트에 0건 — 대각선이 없다.

`@move_speed = 4` (RGSS 척도 1~6 중 "보통"). 대시·달리기 버튼은 존재하지 않는다.

이동은 두 게이트 뒤에 있다. `moving?` — 한 걸음이 끝나기 전에는 다음 입력을 받지 않는다. `map_interpreter.running?` — 이벤트가 도는 동안에는 움직일 수 없다.

*추정:* RGSS 척도 4 에서 한 타일은 8프레임이고, RGSS XP 의 통상 프레임률이 40fps 이므로 **타일당 약 200ms**다. 40fps 는 스크립트에서 직접 확인되지 않은 외부 지식이므로 이 값은 확인된 사실이 아니다.

### 2.2 상호작용 — 확인됨, 그리고 채집 전용이 아니다

채집 노드는 **`trigger = 0` (결정 버튼), `through = false` (통과 불가)** 인 스톡 RGSS 이벤트다. 여기서 두 가지가 따라 나온다.

- 노드는 단단하다. 그 칸에 올라설 수 없다. "옆에 서서 바라본다" 가 유일한 접근 자세다.
- 결정 버튼 트리거는 **인접 + 바라봄**을 요구한다. 옆에 있어도 다른 곳을 보고 있으면 반응하지 않는다.

입력은 `Input.trigger?(Input::C)` — **누를 때마다 한 번**이지, 누르고 있으면 반복되는 것이 아니다.

**중요: 채집 전용 버튼은 존재하지 않는다.** 얼음채집장(Map007)의 이벤트 29개 중 채집 노드는 6개뿐이고, 나머지 23개 — 오크, 채집장 노인, 퀴즈 도우미, 소환물 — 가 전부 같은 `trigger = 0`, 같은 앞칸 + C 버튼이다. **원작에서 "앞칸을 향해 결정 버튼"은 세계와 상호작용하는 유일한 동사다.** 채집은 그 동사의 한 가지 쓰임일 뿐이다.

재진입은 `map_interpreter.running?` 가 막는다. 이전 채집의 딜레이가 끝나기 전에는 다음 채집이 시작되지 않는다 — 별도의 연타 제한 코드가 있는 것이 아니라 이벤트가 아직 돌고 있어서 막힌다.

### 2.3 채집 딜레이의 실제 값 — 확인됨, 이전 문서의 수치는 틀렸다

공용 이벤트 260 이 등급·아이템·버프를 보고 `Wait(n)` 을 고른다. RGSS 의 `Wait` 는 `@wait_count = params[0] * 2` 이므로 파라미터의 두 배가 프레임 수다.

| 상태 | Wait 파라미터 | 프레임 | 40fps 기준 |
|---|---|---|---|
| 아무 부스트 없는 무료 등급 | 8 | 16 | **약 400ms** |
| 개발용·광고 버프·최상위 등급 | 2 | 4 | **약 100ms** |

즉 원작의 실제 범위는 **400ms → 100ms (초당 2.5회 → 10회)** 다.

> **정정:** `packages/shared/src/formulas/proficiency.ts` 의 `ACTION_INTERVAL_MIN_MS` 주석은 50ms 를 "원작의 가장 짧은 채집 딜레이" 라고 적고 있으나 사실이 아니다. 원작의 최속은 100ms 다. **값 자체(500ms → 50ms)는 사용자가 승인한 설계 결정이므로 바꾸지 않고, 원작과 같다는 주석만 바로잡는다.**

### 2.4 자원마다 고갈 여부가 다르다 — 확인됨, 이 설계에 결정적이다

Map171 의 튜토리얼 대사가 자원별로 명시한다.

- 얼음류: 고갈되지 않는다. 한 자리에서 계속 채집할 수 있다.
- 나무류: 고갈되지 않는다.
- 광물류: 채집하다 보면 고갈되어 없어진다. 없어지면 다른 것을 캔다.
- 허브류: 고갈된다.

**우리 `nodes.csv` 의 채집 기술 네 개(ice·wood·mineral·herb)가 정확히 그 넷이다.**

이것이 왜 결정적인가. 고갈이 없으면 플레이어는 접속 후 몇 초만 이동하고 그 뒤로는 한 칸에 서 있는다. 방향 패드는 세션당 한 번 쓰이는 버튼이 되고, 화면 왼쪽 아래를 영원히 가리는 대가만 남는다. **고갈이 있어야 이동이 루프의 일부가 된다.**

> **선행 스펙 정정:** 숙련도 설계 문서는 "원작에 노드별 리스폰 개념이 없다"고 적었다. 그것은 **노드별 쿨다운 타이머**가 없다는 뜻으로는 맞지만, 노드가 무한하다는 뜻으로는 틀렸다. 광물과 허브는 소모된다.

### 2.5 연타를 없애는 버프 — 사실과 해석을 나눈다

**사실:** 각 자원의 원로 NPC 가 25만 골드짜리 채집 버프를 판다. 이 버프는 그 자원 노드의 이벤트 페이지를 `trigger = 0` (결정 버튼) 에서 `trigger = 1` (플레이어 접촉) 으로 바꾼다. `Game_Character#move_down` 등이 이동이 막힐 때마다 `check_event_trigger_touch` 를 부르므로, 접촉 트리거가 된 노드를 향해 방향키를 누르고만 있으면 막힌 걸음마다 채집이 다시 발동한다. NPC 대사도 그렇게 말한다. (얼음에서 확인했고 나머지 셋은 같은 패턴으로 추정한다.)

**해석:** 이것은 편의 기능인 동시에 동기 구조다. 400ms 간격을 몇 시간씩 손가락으로 두드리는 것은 실제로 고되고, 그 고됨이 25만 골드를 벌 이유가 된다. 다만 원작의 기본 간격이 400ms(초당 2.5회)였다는 점은 손가락 병목이 **우리 게임만큼 극단적이지는 않았다**는 뜻이기도 하다. 우리는 최속이 50ms(초당 20회)라 병목이 훨씬 심하다. 이 차이를 5.3 에서 다룬다.

### 2.6 안티매크로 — 확인됨

공용 이벤트 252 가 채집당 1/500 확률로 세 자리 난수를 띄우고 입력을 요구한다. **무과금 등급에서만** 발동한다.

### 2.7 컨트롤러 배치 — 확인 불가, 대사로만 알 수 있다

원작 APK 는 껍데기 로더이고 화면 위 컨트롤러는 별도 앱 "Neko RPGXP Player" 가 그린다. 그 앱이 자료에 없어 **버튼 이미지·픽셀 크기·화면 방향 고정 여부는 확인할 수 없다.**

게임 자신의 튜토리얼(Map171 "조작법")이 배치를 말로 설명한다: **왼쪽에 방향키, 오른쪽에 4버튼 묶음** — 묶음의 왼쪽 아래가 결정(C), 오른쪽 아래가 취소(B), 위쪽이 특수 메뉴.

## 3. 무엇을 가져오고 무엇을 바꾸나

### 3.1 그대로 가져온다

| | 이유 |
|---|---|
| 4방향 타일 이동, 대각선 없음 | 앞칸이 하나로 정해져야 판정이 모호해지지 않는다 |
| 노드는 단단하다 | 올라설 수 없어야 "옆에 서서 바라본다"가 강제된다 |
| 인접 + 바라봄 | 위치가 규칙이 되는 유일한 지점이다 |
| **앞칸 + 결정 버튼이 세계와 상호작용하는 유일한 동사** | 2.2 의 발견. 채집만을 위한 입력을 만들면 NPC·이벤트·전투가 들어올 문이 없다 |
| 한 번 누르면 한 번 | 반복의 육체성이 여기서 나온다 |
| 걸음 중 입력 무시 | 이동이 이산적이려면 필요하다 |

### 3.2 바꾼다

**컨트롤러를 우리가 그린다.** 배치는 원작의 말로 된 설명을 따른다.

**자동 반복의 대가가 골드가 아니라 숙련도다.** 5.3 에서 설명한다.

**안티매크로는 만들지 않는다.** 원작에서 그것은 무과금 등급의 가치를 낮춰 과금을 유도하는 장치였다. 과금이 없는 게임에서 같은 것을 넣으면 순수한 마찰만 남는다. 봇이 실제 문제가 되는 시점 — 경매장이 생긴 뒤 — 에 다시 판단한다.

**대각선을 넣지 않는 것은 결정이다.** 현대 모바일의 관례는 8방향이고 지금 코드도 8방향이다. 그래도 4방향으로 되돌린다.

## 4. 입력 추상화

키보드와 화면 버튼은 **같은 하나의 입력 상태**에 쓴다. 게임 로직은 어느 장치인지 모른다.

```ts
interface InputState {
  dir: Direction | null    // 4방향만
  action: boolean          // 눌려 있는가 (자동 반복용)
  actionPressed: boolean   // 이번 프레임에 새로 눌렸는가
  cancel: boolean
  toggleBag: boolean
  toggleCraft: boolean
}
```

두 소스가 이 상태에 기여한다.

- **KeyboardSource** — WASD·방향키, 스페이스/J(action), Esc/K(cancel), I(가방), C(제작). PC 개발용.
- **TouchSource** — 화면 위 가상 컨트롤러.

동시에 눌리면 마지막으로 바뀐 쪽이 이긴다. 실기에는 키보드가 없고 PC 에는 터치가 없으므로 병합 규칙을 복잡하게 만들지 않는다.

나중에 게임패드 소스를 붙일 수 있다 — 그것이 이 추상화의 값어치다. 지금 만들지는 않는다.

## 5. 이동과 상호작용의 규칙은 `packages/shared` 에 둔다

이 프로젝트의 제1원칙은 **게임 규칙이 `packages/shared` 에만 존재한다**는 것이다. 인접·바라봄·걸음 간격은 명백히 규칙이다 — 서버가 위치를 알게 되는 순간 서버가 검증할 것들이다. 클라이언트에만 두면 나중에 서버에 같은 것을 다시 구현하게 되고, 그것이 정확히 이 원칙이 금지하는 일이다.

`packages/shared` 에 들어가는 것:

```ts
type Direction = 'up' | 'down' | 'left' | 'right'
interface TilePos { x: number; y: number }

const STEP_MS: number              // 한 걸음에 걸리는 시간
const REPEAT_UNLOCK_PROFICIENCY: number

function frontTile(pos: TilePos, facing: Direction): TilePos
function isAdjacentFacing(from: TilePos, facing: Direction, target: TilePos): boolean
function canRepeat(proficiency: number): boolean
```

클라이언트가 이 함수들로 판정하고, 서버는 위치 동기화 스펙이 나올 때 **같은 함수**로 검증한다.

### 5.1 이동 모델

플레이어는 항상 정확히 한 타일 위에 있다. **정본 위치는 타일 정수 좌표**이고, 픽셀 좌표는 그것을 그리기 위한 파생물이다. 이 순서가 뒤집히면 위치를 서버에 보낼 때 반올림 문제가 생긴다.

방향 입력이 들어오면:

1. **바라보는 방향을 즉시 그 방향으로 바꾼다.** 걸을 수 있든 없든.
2. 앞칸이 걸을 수 있으면 한 걸음을 시작한다.
3. 걸음이 끝날 때까지(`STEP_MS`) 새 방향 입력을 받지 않는다.

1번이 2번과 분리된 것이 중요하다. 벽이나 노드를 향해 방향키를 누르면 움직이지 않지만 **그쪽을 바라보게 된다.** 노드 앞에 서서 방향을 맞추는 조작이 여기서 나온다.

걸음이 끝난 시점에 방향키가 여전히 눌려 있으면 곧바로 다음 걸음을 시작한다.

### 5.2 왜 자유 이동이 아니라 타일인가

1. **앞칸이 하나로 정해진다.** 자유 이동에서 "무엇을 바라보는가"는 각도 문제가 되고, 임계값이 생기고, 임계값은 반드시 애매한 경계를 만든다.
2. **온라인.** 자유 위치는 연속 좌표 스트림과 보간과 조정을 요구한다. 타일 걸음은 이산 사건이다 — "(3,5)에서 (3,6)으로" 한 줄이면 되고, 순서가 자명하고, 서버가 검증할 수 있다("인접한가, 걸을 수 있는 칸인가, 걸음 간격을 지켰는가"). 한 화면에 여러 플레이어가 목표인 이상 나중에 바꾸기 매우 비싸다.
3. **원작의 감각.**

이 스펙은 위치를 서버에 보내지 않는다. **보낼 수 있는 모양으로 만들 뿐이다** — 그리고 그 모양을 실제로 만든다(정본이 타일 좌표, 규칙이 shared, 노드에 인스턴스 정체성).

### 5.3 자동 반복은 숙련도가 연다

**문제.** 우리 게임의 최속은 50ms — 초당 20회다. 손가락으로 낼 수 있는 속도가 아니다. 원작처럼 골드로만 열 수 있게 두면, **가장 오래 판 플레이어가 자기가 번 속도에 가장 못 닿는다.** 경제가 아직 없으므로 그것은 "언젠가 열림"이 아니라 "영원히 안 열림"이다. 갈망이 아니라 벌이다.

**해결.** 자동 반복을 **기술별 숙련도 문턱**으로 연다.

```
REPEAT_UNLOCK_PROFICIENCY = 10_000   // actionIntervalMs(10_000) = 200ms = 초당 5회
```

그 기술의 숙련도가 10,000 을 넘으면 그 기술의 노드 앞에서 행동 버튼을 누르고 있는 동안 반복된다. 넘기 전에는 누르고 있어도 아무 일도 일어나지 않는다.

**왜 이 값인가.** 초당 5회는 손가락으로 지속하기 어려운 경계다. 즉 해금이 **정확히 손가락이 병목이 되는 순간**에 온다. 그 전까지는 연타가 실제로 가능하므로 잠겨 있어도 손해가 없고, 그 뒤로는 잠겨 있으면 손해이므로 열린다. 숙련도 10,000 은 채집 기준 약 30분이다.

**기술마다 따로 연다.** 원작이 자원별로 따로 팔았던 구조를 유지한다. 채집 4종 + 조합 = 다섯 번의 작은 목표가 된다.

**해금은 사건이어야 한다.** 조용히 켜지면 아무도 알아채지 못한다. 원작이 8,000시간을 버틴 이유가 노가다 사이사이의 사건이라면, 이것은 그 첫 번째 사건이 될 수 있다. 넘는 순간 화면에 명시적으로 알린다 — 수치 알림이 아니라 그 기술이 손에 익었다는 말로.

**골드 경로는 버리지 않는다.** 경제가 생기면 "문턱보다 일찍 여는 두 번째 경로"로 붙인다. 원작의 씨앗이 그대로 남는다.

### 5.4 상호작용 대상은 노드가 아니라 `Interactable` 이다

2.2 에서 확인했듯 원작에서 앞칸+결정 버튼은 세계와 상호작용하는 **유일한 동사**다. 채집만을 위해 이 경로를 만들면 NPC·이벤트·전투 진입점이 들어올 문이 없다 — 그리고 그것들이야말로 이 게임이 살려야 할 부분이다.

그래서 앞칸이 담는 것을 `Interactable` 로 정의한다.

```ts
type Interactable =
  | { kind: 'node'; instanceId: string; nodeId: string }
  // 이후 스펙이 여기에 더한다: npc, event, portal, ...
```

`actionPressed` 가 참이고 앞칸에 `Interactable` 이 있으면 그 종류에 맞는 처리를 부른다. 지금은 `node` 하나뿐이지만, 새 종류를 더하는 데 입력 계층을 건드릴 필요가 없다.

### 5.5 노드에 인스턴스 정체성을 준다

지금 `world.json` 에는 같은 `nodeId` 가 여러 칸에 있다 — `copper_vein` 2개, `ice_vein` 2개, `young_tree` 2개. 그런데 채집 요청은 `{ nodeId }` 하나만 보낸다. **서버가 받는 것은 "어느 노드"가 아니라 "어느 종류"다.**

앞칸 판정을 서버가 검증하려면 어느 칸인지 알아야 하고, 고갈을 넣게 되면 필수가 된다. 그래서 지금 넣는다.

- 맵의 각 노드 오브젝트가 고유한 `instanceId` 와 타일 좌표를 갖는다
- 채집 요청이 `{ instanceId }` 를 보낸다
- 서버는 `instanceId` → `nodeId` + 타일 좌표를 안다

이동만 모양을 갖추고 상호작용은 안 갖추면 5.2 의 논거가 절반만 선다.

### 5.6 서버가 아직 강제하지 못하는 것 — 정직하게 적어 둔다

인접과 바라봄은 **지금 클라이언트에서만 성립한다.** 서버는 플레이어의 위치를 모르므로, 조작된 클라이언트가 아무 노드나 지정하면 그대로 채집된다.

이것은 결함이 아니라 **범위의 경계**다. 규칙 함수와 인스턴스 id 를 이번에 만들어 두므로, 서버가 위치를 알게 되는 순간 검증은 함수 호출 한 줄이 된다. 그때까지 인접·바라봄은 UI 규칙이지 게임 규칙이 아니다.

싱글 개발 단계에서 실제 위험이 아닌 이유는 속일 상대가 자기 자신뿐이기 때문이다. 플레이어 사이에 가치가 오가기 전에 닫으면 된다.

## 6. 반복 중의 표현

초당 20회로 반복될 때 지금의 표현은 무너진다. `FloatingText` 는 행동마다 새 텍스트를 만들고 900ms 살기 때문에, 같은 자리에 18개가 겹쳐 아무것도 읽을 수 없다.

**반복 중에는 누적해서 보여준다.** 머리 위 글자 하나가 살아 있는 동안 같은 종류의 결과가 또 오면 새로 만들지 않고 그 글자의 수치를 더하고 수명을 늘린다. 반복이 멈추면 자연히 사라진다.

실패는 따로 세지 않는다. 성공 개수만 누적하고, 연속 실패가 이어지면 그때만 실패를 표시한다 — 초당 20번 "실패" 가 뜨는 화면은 정보가 아니라 소음이다.

**요청은 서버의 행동 간격에 맞춰 보낸다.** `nextActionAt` 이전에는 요청 자체를 보내지 않는다. 지금 구조에서 `too_fast` 는 클라이언트가 조용히 삼키므로, 무작정 보내면 "가끔 안 캐진다" 로 보인다. 보내지 않으면 그런 상태가 애초에 생기지 않는다.

## 7. 화면 배치

가로 고정이다. 세로 배치는 만들지 않는다.

```
┌──────────────────────────────────────────────┐
│ [숙련도 바 ............................] [⚙] │  기존 상단 바
│                                              │
│                 게임 화면                     │
│                                              │
│                                    [가방][제작]│
│      ╔═╗                              ╔═╗    │
│    ╔═╣↑╠═╗                          ╔═╣B╠═╗  │
│    ║←╬─╬→║                          ║A╠═╝    │
│    ╚═╣↓╠═╝                          ╚═╝      │
└──────────────────────────────────────────────┘
```

- **왼쪽 아래: 4방향 패드.** 대각선 칸은 없다. 누른 지점에서 가장 가까운 축 방향 하나를 고른다.
- **오른쪽 아래 안쪽: A (행동).** 가장 많이 누르는 버튼이므로 엄지가 자연히 놓이는 안쪽에 둔다. 원작 배치와 같다.
- **A 의 바깥쪽 위: B (취소·패널 닫기).**
- **그 위: 가방·제작 토글.**

컨트롤러는 게임 화면 **위에** 반투명하게 겹친다. 별도 띠를 만들어 화면을 좁히지 않는다 — 가로 화면에서 세로 픽셀은 가장 비싼 자원이다.

버튼은 최소 48dp 상당으로 잡는다. **안드로이드 제스처 내비게이션 영역을 피해야 한다** — 화면 맨 아래 가장자리에서 위로 여백을 둔다. 정확한 값은 실기 확인 후 조정한다.

**패널이 열려 있는 동안 이동과 행동 입력은 막는다.** 원작의 `map_interpreter.running?` 게이트와 같은 성격이다.

## 10. 미룬 결정과 그 기준

**노드 고갈.** 2.4 에서 확인했듯 광물과 허브는 원작에서 고갈된다. 이번 범위에 넣지 않는 이유는 서버의 노드 상태·회복 규칙·여러 플레이어의 공유 문제가 함께 딸려 오기 때문이다.

*이번 증분에서도 이동은 의미가 있다* — 제작 레시피가 여러 기술의 재료를 요구하므로(철 정은 구리 주괴와 얼음 조각을, 철 도끼는 구리 주괴와 통나무를 쓴다) 플레이어는 기술 사이를 오간다. 고갈은 여기에 **같은 기술 안에서의 이동**을 더한다.

*결정 기준:* 위치 동기화 스펙이 나올 때 함께 정한다. 고갈된 노드가 누구에게 고갈된 것인지(플레이어별인가 서버 전역인가)가 온라인 설계와 분리될 수 없기 때문이다.

**컨트롤러 크기와 위치.** 데스크톱 브라우저의 가로 창과 실제 휴대폰의 엄지 도달 범위는 다르다. 안드로이드 실기 확인을 아직 한 번도 하지 못했다. *기준:* 실기에서 한 손 조작으로 A 와 패드에 동시에 닿는지.

**패드를 고정할 것인가 떠 있게 할 것인가.** 고정이 원작에 가깝고 구현이 단순하다. 우선 고정으로 만들고 실기에서 판단한다.

**`STEP_MS` 의 값.** 원작 추정값 200ms 로 시작한다. 원작은 40fps 에 작은 화면이었으므로 그대로가 최선이라는 보장은 없다. 상수로 두고 조정한다.

## 11. 이 스펙이 만드는 것 (요약)

1. `packages/shared` 에 이동·상호작용 규칙 (`Direction`, `TilePos`, `frontTile`, `isAdjacentFacing`, `canRepeat`, `STEP_MS`, `REPEAT_UNLOCK_PROFICIENCY`)
2. 장치를 모르는 `InputState` 와 두 개의 소스 (키보드, 터치)
3. 4방향 타일 이동 — 정본은 타일 좌표
4. 노드 인스턴스 정체성, 맵 데이터와 채집 요청 양쪽에
5. `Interactable` 로 열린 앞칸 상호작용
6. 숙련도가 여는 자동 반복 + 해금을 알리는 사건
7. 반복 중 누적 표현, `nextActionAt` 에 맞춘 요청
8. 가로 화면 가상 컨트롤러
9. 탭 이동·탭 채집 제거
