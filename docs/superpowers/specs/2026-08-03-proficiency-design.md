# 숙련도 시스템 — 설계 문서

**작성일:** 2026-08-03
**상태:** 승인됨 (구현 계획 대기)
**관련 문서:** [프로젝트 설계](2026-08-02-nogada-rpg-fanmade-design.md) · [세계 시간](2026-08-02-world-time-design.md)

---

## 1. 개요

### 1.1 목적

경험치·레벨 곡선으로 만들어져 있는 현재 숙련도를 **원작과 같은 계열의 누적 카운터**로 바꾼다. 그리고 그 숫자가 **행동 속도·성공률·수량**을 정하게 해서, 오래 할수록 스스로 빨라지는 노가다 구조를 만든다.

### 1.2 범위

서버 판정과 공식, 데이터 스키마까지다. **조작 방식은 이 문서에서 다루지 않는다** — WASD 컨트롤러, 노드 인접 판정, 상호작용 키 연타는 별도 문서에서 설계한다. 이 문서의 변경만으로는 기존 탭 조작이 그대로 동작한다.

### 1.3 비목표

- 조작 방식 변경 (컨트롤러·인접 판정·연타)
- 명상·낚시 — 상호작용형과 다른 행동 방식이라 별도 설계가 필요하다
- 효율 배수의 **공급원** (장비·설정·버프). 식에 자리는 만들되 올리는 수단은 만들지 않는다
- 원작에 있던 과금 등급·광고 버프. 설계 문서 1.3 이 과금을 비목표로 못 박았다

## 2. 원작 조사 결과

APK(v2.1, RPG Maker XP)의 `Game.rgssad` 를 풀어 커먼이벤트 971개와 이름 붙은 변수 1,542개를 확인했다. 아래는 그 결과이며, 이 설계의 근거다.

### 2.1 숙련도는 정수 변수 하나씩이다

숙련도 관련 변수 30개가 각각 독립된 정수다. 경험치도 레벨 곡선도 없다. 채집계 넷(얼음·나무·광물·허브)은 변수 번호가 연달아 배치돼 있어 같은 계열로 설계된 흔적이 보인다.

### 2.2 채집은 소량 고정, 제작은 등급 비례

| | 1회 증가량 |
|---|---|
| 채집 이벤트 | **+1 또는 +1~2.** 등급이 높은 노드도 같다 |
| 최상위 제작 | **한 번에 수만~십수만** |

**채집에서 상위 노드에 가는 이유는 숙련도가 아니라 재료다.** 이 성격 구분을 그대로 가져온다.

### 2.3 속도는 딜레이 단계로 조절됐고, 숙련도와 무관했다

채집 딜레이는 0·2·4·6·8 프레임 중 하나이고(40fps 기준 0~200ms), 이 값을 정하는 것은 **옵션 메뉴 + 과금 등급 + 광고 시청 버프**였다. 숙련도가 이 변수를 건드리는 코드는 없다.

체감상 "고인물이 빨라진다" 였던 것은 오래 한 사람일수록 과금 등급이 높았기 때문으로 보인다.

### 2.4 그래서 이 설계가 바꾸는 축

이 프로젝트는 과금을 만들지 않는다. **속도를 정하는 축을 과금 등급에서 숙련도로 옮긴다.** 원작의 체감(오래 할수록 빨라진다)은 유지하면서 수단만 바꾸는 것이다.

이 치환이 이 문서에서 원작과 다른 유일한 지점이며, 나머지는 원작 구조를 따른다.

## 3. 숙련도 모델

### 3.1 자료 구조

```
SkillState { level, xp }   →   number
```

`PlayerState.skills` 는 `Record<SkillId, number>` 가 된다. 값은 그 행동을 성공한 누적량이며 상한을 두지 않는다(실용 범위 10⁸).

### 3.2 숙련도 종류

| id | 이름 | 계열 |
|---|---|---|
| `ice` | 얼음 | 상호작용 채집 |
| `wood` | 나무 | 상호작용 채집 |
| `mineral` | 광물 | 상호작용 채집 |
| `herb` | 허브 | 상호작용 채집 |
| `crafting` | 조합 | 제작 |

기존 `mining`·`smithing` 은 사라진다. 명상·낚시·헌혈 등은 행동 방식이 달라 별도 설계 후에 추가한다.

### 3.3 증가량

증가량은 **데이터가 정한다.** 노드와 레시피가 각자 `skillGainMin`·`skillGainMax` 를 갖고, 판정 시 그 범위의 정수를 뽑는다.

| | 기본값 |
|---|---|
| 채집 노드 | 1 ~ 2 (등급과 무관) |
| 제작 레시피 | 요구 숙련도에 대략 비례 |

제작 증가량의 기준점을 못 박아 둔다. 테스트 맵 레시피는 이 표를 따르고, 이후 레시피도 같은 자릿수 감각으로 정한다.

| 요구 조합 숙련도 | 1회 증가량 |
|---|---|
| 0 (시작 레시피) | 10 ~ 20 |
| 1,000 | 60 ~ 100 |
| 100,000 | 900 ~ 1,500 |
| 10,000,000 | 40,000 ~ 70,000 |

대략 **요구 숙련도의 0.5~1%** 다. 최상위 구간이 원작에서 확인한 수만~십수만과 같은 자릿수에 놓인다.

식에 효율 배수 자리를 둔다.

```
증가량 = rollInt(skillGainMin, skillGainMax) × 효율배수
```

**효율배수는 이번 범위에서 항상 1이다.** 자리를 미리 만들어 두는 이유는, 나중에 배수를 도입할 때 저장된 숙련도의 의미나 증가 경로를 다시 손대지 않기 위해서다.

## 4. 숙련도가 정하는 것

세 공식 모두 `packages/shared` 에 두고 서버와 클라이언트가 함께 import 한다. 클라이언트는 예상치 표시에만 쓰고 판정은 서버가 한다.

공통 진행도:

```
t(s) = min(1, log₁₀(s + 1) / D)
```

`s` 는 숙련도, `D` 는 공식마다 다른 자릿수 기준이다. 로그를 쓰는 이유는 유효 범위가 8자릿수라 선형식이 두 자릿수 안에서 상한에 닿아버리기 때문이다.

### 4.1 행동 간격 — 핵심 축

```
간격(ms) = 500 − 450 × t(s),  D = 6
```

| 숙련도 | 간격 | 초당 |
|---|---|---|
| 0 | 500ms | 2.0회 |
| 1,000 | 275ms | 3.6회 |
| 10,000 | 200ms | 5.0회 |
| 100,000 | 125ms | 8.0회 |
| 1,000,000 이상 | 50ms | 20회 |

양 끝은 원작과 같다 — 시작 초당 2회, 최대 초당 20회. 100만에서 최고속에 닿고 그 뒤로는 숫자만 쌓인다.

**검산:** 평균 증가량 1.5 기준으로 100만까지 약 31시간, 거기서 5,000만까지 약 453시간, 합계 **약 484시간**. 원작 플레이 경험(8,000시간 중 얼음 5,000만)과 같은 자릿수다.

간격은 **행동 종류와 무관하게 플레이어당 하나**다. 채집이든 제작이든 마지막 행동 시각 하나를 보고 판정한다. 숙련도별로 나누면 여러 기술을 번갈아 눌러 실질 속도를 배로 올릴 수 있다.

### 4.2 성공률

```
성공률 = base + (0.98 − base) × t(s),  D = 5      [0.05, 0.98] 로 클램프
```

`base` 는 노드가 정한다. 10만에서 상한에 닿는다.

상한을 1.0 이 아니라 0.98 로 두는 이유는 판정이 살아 있다는 것을 유지하기 위해서다. 반대로 영구 실패율을 크게 두지 않는 이유는, 초당 20회를 누르는 게임에서 잦은 실패는 난이도가 아니라 소음이기 때문이다.

### 4.3 수량

```
수량 = rollInt(yieldMin, yieldMax) + floor(t(s) × 2),  D = 5
```

숙련도 보너스를 최대 +2 로 묶는다. 속도가 이미 10배까지 복리로 작용하므로 수량까지 크게 굴리면 곱셈이 과해진다.

## 5. 구조 변경

### 5.1 노드별 쿨다운을 없앤다

`PlayerState.nodeCooldowns` 를 지우고 `nextActionAt: number` 하나로 대체한다.

원작에 노드별 리스폰 개념이 없다. 속도를 정하는 것은 노드가 아니라 행동 간격이며, 플레이어는 한 노드 앞에 서서 반복해서 캔다. 노드는 이제 **"무엇이 얼마나 나오는가"** 만 정한다.

이 변경은 M1 검증에서 발견된 문제도 함께 없앤다 — 같은 종류 노드 여러 개가 쿨다운을 공유해 맵에 6개를 놓아도 채집원이 하나였던 것은, 노드별 쿨다운이라는 설계 자체가 원작과 어긋나서 생긴 증상이었다.

### 5.2 접근 게이트는 도구 등급만

노드에서 `requiredLevel` 을 제거한다. 채집 노드를 여는 것은 **도구 등급 하나뿐**이다.

M1 검증에서 강화 곡괭이(2등급)를 만들고도 철 광맥이 열리지 않았다. 도구와 숙련도 두 개의 문이 겹쳐 있어서, 제작으로 도구를 얻어도 채집을 더 해야 했다. 문을 하나로 줄이면 설계 문서 5.1 의 핵심 루프(채집 → 제작 → 더 좋은 도구 → 상위 채집)가 곧바로 성립한다.

제작에는 도구 게이트가 없으므로 **조합 숙련도가 레시피를 연다.** 레시피의 `requiredLevel` 은 `requiredSkill` 로 이름을 바꾸고 새 척도의 값을 갖는다.

### 5.3 서버가 간격을 강제한다

행동 요청이 오면 서버가 자기 시계로 `nextActionAt` 을 검사한다. 이르면 거부하고, 처리하면 `now + 간격(숙련도)` 으로 갱신한다. 클라이언트의 간격 계산은 표시·입력 억제용이며 판정 근거가 아니다.

**검사 순서를 못 박는다.**

```
1. 대상이 존재하는가        (unknown_node / unknown_recipe)
2. 접근 조건을 만족하는가    (cannot_gather / level_too_low)
3. 재료가 있는가            (missing_materials — 제작만)
4. 간격이 지났는가          (too_fast)
5. ── 여기서부터 난수를 굴린다 ──
```

간격 검사를 **난수보다 앞, 자격 검사보다 뒤**에 두는 이유가 각각 있다. 난수보다 앞인 것은, 거부된 요청이 시드를 소비하면 연타로 판정 결과를 흔들 수 있기 때문이다. 자격 검사보다 뒤인 것은, 캘 수 없는 노드를 두드리는 것이 간격까지 잡아먹으면 안 되기 때문이다 — 자격 미달은 조작 실수이지 속도 위반이 아니다.

간격 갱신은 **판정을 실제로 수행한 경우에만** 한다. 성패와는 무관하다 — 실패도 한 번의 행동이다.

거부 코드는 `too_fast` 다. 기존 `on_cooldown` 과 마찬가지로 **화면에 아무것도 띄우지 않는다** — 연타가 정상 조작인 게임에서 매번 알리면 화면이 경고로 덮인다.

## 6. 데이터 스키마

### 6.1 `nodes.csv`

| 열 | 변경 |
|---|---|
| `skill` | 새 id (`ice`/`wood`/`mineral`/`herb`) |
| `requiredLevel` | **제거** |
| `respawnMs` | **제거** |
| `baseChance` | **추가** — 숙련도 0 일 때의 성공률 |
| `skillGainMin` · `skillGainMax` | **추가** — 기본 1 ~ 2 |

`tier`, `yieldItem`, `yieldMin`, `yieldMax` 는 유지한다.

### 6.2 `recipes.csv`

| 열 | 변경 |
|---|---|
| `skill` | `crafting` 고정 (당분간) |
| `requiredLevel` | → `requiredSkill` (새 척도) |
| `skillGainMin` · `skillGainMax` | **추가** |

### 6.3 `items.csv`

도구의 `toolSkill` 을 새 id 로 바꾼다. 테스트 맵에서 네 채집 기술을 모두 시험할 수 있도록 기술별 시작 도구를 둔다.

### 6.4 검증

`packages/data` 의 빌드 타임 검증에 규칙을 더한다.

- `skillGainMin ≤ skillGainMax`, 둘 다 1 이상
- `baseChance` 는 0 초과 1 미만
- `requiredSkill` 은 0 이상
- 기존 규칙(참조 무결성, 도달 가능성, `STARTING_TOOL_IDS` 검사)은 유지

## 7. 기존 세이브

**마이그레이션하지 않는다.** 개발용 테스트 세이브 하나뿐이고 숙련도 종류가 통째로 바뀌므로, 변환 코드는 쓸모없는 복잡도만 남긴다. 서버는 형식이 맞지 않는 세이브를 발견하면 버리고 새 플레이어를 만든다.

실제 유저 데이터가 생기기 전에 이 결정을 뒤집어야 한다 — M4(온라인 개방) 이전에 마이그레이션 장치를 갖춘다.

## 9. 테스트 전략

| 대상 | 방식 |
|---|---|
| `proficiency.ts` | **유닛 테스트를 두껍게.** 8자릿수 범위의 경계값, 단조성, 상·하한 |
| `gather`·`craft` 공식 | 새 인자로 갱신 |
| `gatherService`·`craftService` | 간격 거부(`too_fast`), 숙련도 증가량, 수량 보너스 |
| `packages/data` | 새 검증 규칙마다 위반 케이스 |
| 클라이언트 UI | 기존 방침대로 자동 테스트하지 않는다 |

`actionIntervalMs` 는 특히 손으로 검산한 값을 테스트에 박는다 — 이 함수 하나가 게임 전체의 속도를 정하므로, 리팩터링이 곡선을 바꾸면 즉시 드러나야 한다.
